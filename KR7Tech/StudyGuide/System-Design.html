System design concepts, connected into one clear model

System design is not choosing technologies from a list. It is a chain of reasoning: understand the workload, state what must remain true, place ownership, choose the simplest architecture that meets the targets, then prove it behaves safely under load and failure.

1 · WorkloadWho does what, how often, and in what bursts?
2 · PromiseWhat must be correct, fast, available, or durable?
3 · AuthorityWhich component owns each important fact?
4 · BoundariesWhat must happen together; what can happen later?
5 · FailureWhat if a timeout, retry, or dependency outage occurs?
6 · EvidenceWhich metric or test proves the design meets its promise?

1. Workload is more than “users”

Translate users into operations: browse, search, checkout, upload, or background work. Estimate average and peak arrival rate, concurrency, payload size, read/write mix, hot keys, and growth. A thousand mostly-idle users can be easier than one popular product hit by a sudden burst.

in-flight work ≈ arrival rate × average response time

Example: 200 requests/second × 0.25 seconds ≈ 50 requests in flight on average. This is a starting estimate, not the capacity target; peak bursts and headroom still matter. Continue in sizing and traffic shifts.

2. An invariant is a rule that must never be violated

Write the business rule before picking a database. MarketSquare’s invariant: the same unit of inventory cannot be reserved for two active orders. The authoritative inventory owner must enforce that rule atomically; checking a cached count and then writing later is a race.

available = on hand − active reservations − sold

Use a conditional update, constraint, or transaction at the owner of the stock. Search and cache may show an approximate hint, but checkout must consult the authority. See transactions and LLD.

3. A consistency boundary is not always a service boundary

Facts that must change together belong inside a short atomic transaction when possible. A modular monolith can have clear domain ownership while sharing one database transaction. Notifications and search indexing can happen later because they do not decide whether an order is valid.

Rule of thumb: split a deployment boundary only when independent ownership, scaling, release, or isolation is worth the added network failures, duplicated data, retries, and operations. Read advanced HLD and architecture patterns.

4. End-to-end latency is a budget

A request’s response time includes network hops, queueing, application work, and dependencies. Sequential calls add latency; parallel calls finish when the slowest required branch finishes. Percentiles expose the slow tail: a good average can hide a poor p95 or p99 experience.

request deadline = total budget shared across all required hops

Set a deadline, propagate its remaining time, and ensure retries fit inside it. Measure each hop and queue wait before optimizing. See network path and traffic control.

5. Async means “later and recoverable,” not “guaranteed once”

A queue decouples work and absorbs bursts, but consumers may receive a message more than once, out of order, or after a delay. Persist business state and an outbox event together; publish from the outbox; make each consumer idempotent. Show users pending states honestly while projections catch up.

Example: an order is confirmed by its owner first; search, email, and analytics update asynchronously. A delayed email must never undo or redefine the order. Continue in cache and messaging.

6. Overload can create a retry feedback loop

When a dependency slows, callers wait longer, concurrency grows, timeouts trigger retries, and retries add more load to the already-slow dependency. Adding app instances may worsen this if the database is the bottleneck.

Break the loop: deadlines, bounded retries with jitter, concurrency limits, backpressure, admission control, and graceful degradation of optional work. A circuit breaker stops calls temporarily; it does not itself queue work or set a fair per-user quota. See reliability and incident lab.

Put the model together: a flash sale creates a hot product

  1. Workload: most requests target one SKU, so total traffic hides a hot-key and database-lock problem.
  2. Promise: product pages may be briefly stale, but the system must not oversell the last unit.
  3. Authority: inventory owns reservation; CDN/cache/search data is only a display projection.
  4. Boundary: reserve stock and create the durable order intent safely; send optional updates asynchronously.
  5. Failure: use idempotency for client retries, bounded provider calls, and a pending state when payment outcome is unknown.
  6. Evidence: observe per-SKU cache hit rate, database lock waits, checkout p95/p99, payment timeouts, retry rate, and oversell count.

Design conclusion: protect the invariant first, then improve throughput without moving ownership to a stale cache. Work through the full flash-sale scenario for detailed flows and mitigations.

Topic 1 · Queueing theory: why latency explodes before a service is “full”

Why it matters: requests do not arrive evenly. If work arrives faster than a constrained dependency completes it, requests wait in a queue. Waiting consumes connections, memory, and deadlines. Timeouts trigger retries, which add more arrivals and can create a positive feedback loop.

Arrival rate λRequests / second
→
Bounded workersOnly N operations can run
→
Dependency μDB/provider service rate
→
Queue + deadlineWait, reject, or shed safely

How to reason: Little’s Law says average in-flight work L = λW. At 200 requests/second and 250 ms average time, expect about 50 requests in flight. If a database pool can serve 40 checkout operations/second but 60 arrive/second, the backlog grows by about 20/second until arrivals fall or capacity changes. This simplified example ignores burstiness and service-time variation; real systems need load tests.

As utilization approaches 100%, small bursts and slow requests create disproportionately long waits. Do not solve this by raising every limit: that may move the queue into the database and exhaust its connections. Bound concurrency at the scarce resource, shed or defer work with a clear response, and reserve capacity for critical operations.

ASP.NET Core example · cap per-process checkout concurrency 
var checkoutSlots = new SemaphoreSlim(80, 80);

app.MapPost("/checkout", async (
    CheckoutRequest request,
    ICheckoutService checkout,
    CancellationToken cancellationToken) =>
{
    if (!await checkoutSlots.WaitAsync(0, cancellationToken))
        return Results.StatusCode(StatusCodes.Status503ServiceUnavailable);

    try
    {
        return Results.Ok(await checkout.CreateAsync(request, cancellationToken));
    }
    finally
    {
        checkoutSlots.Release();
    }
});

The limit of 80 is an example, not a recommendation. A process-local semaphore multiplies by the number of app instances; it is not a global quota. Select the limit from database-pool budgets and load tests, return a retry hint where safe, and ensure the client uses bounded retries with jitter.

Measure: arrival/completion rate, active and waiting requests, queue age, p95/p99 latency, timeout/retry rate, DB pool wait, lock wait, and downstream saturation. See traffic control and traffic shifts.

Topic 2 · Sagas and the transactional outbox: recover across independent systems

Why it matters: a SQL transaction cannot atomically commit both a database row and a remote payment-provider action. Holding a database transaction open during a network call ties up locks and connections, yet a crash can still occur after the provider acts and before your app records the result.

1 · Order DBCommit Pending order + PaymentRequested outbox row
→
2 · Outbox relayPublish durable message; mark delivered
→
3 · Payment workerCall provider with stable idempotency key
→
4 · Result ownerRecord outcome + next outbox event
Failure path: unknown provider result → keep order/payment Pending → query provider or consume signed callback → reconcile → confirm or release reservation according to policy. Never guess “failed” from a timeout.

How to build it: each step is a local transaction with a durable state transition. The saga is a workflow, not a magic distributed rollback. A compensation (such as releasing a reservation) is a new business action; it may itself fail and must be retryable. Define which states are terminal, how late payment is handled, and how an operator can repair a stuck workflow.

SQL shape · save business intent and event together 
BEGIN;

INSERT INTO orders (order_id, status, idempotency_key)
VALUES (:order_id, 'PENDING_PAYMENT', :request_key);

INSERT INTO outbox (event_id, aggregate_id, event_type, payload)
VALUES (:event_id, :order_id, 'PaymentRequested', :payload);

COMMIT;

The relay may publish and crash before marking the row delivered, so it can publish again. Consumers must deduplicate with a durable event/business key and commit their deduplication record with their own side effect. “Exactly once” is achieved as an idempotent business effect, not assumed from transport delivery.

Observed outcomePersisted stateSafe next action
Provider confirms successPayment = Succeeded; order transition is conditionalEmit OrderConfirmed once; fulfill idempotently
Provider confirms declinePayment = Declined; order remains unconfirmedRelease reservation through an idempotent compensation
Request times out / response unknownPayment = Unknown or PendingQuery by provider key/reference or reconcile callback; do not send a new logical charge

Test: crash after DB commit, after publish, after provider success, and before local result commit. Re-run each operation and prove there is still one order, one logical charge, and a recoverable state. See reliability and distributed primitives.

Topic 3 · Replicas and read-your-writes: explain what “stale” means

Why it matters: a primary can acknowledge a write before an asynchronous replica has replayed it. A shopper updates an address, then immediately reads from a lagging replica and sees the old value. Replication improves read capacity and recovery options; it does not automatically provide read-after-write consistency.

Client writesUpdate address
→
Primary commits v42Returns commit version / token
→
Replica is v40It has not replayed the write
→
Read policyRoute to primary or wait boundedly for v42

How to choose: use the primary for checkout, authorization, and immediate confirmation when stale data could violate an invariant. For a profile or catalog read, a short stale window may be acceptable. For read-your-writes, return a version/commit token and route the caller to the primary (or wait briefly for a replica watermark); if the bound expires, return an explicit pending/stale result rather than silently claiming the update disappeared.

Optimistic concurrency · reject a stale edit instead of overwriting newer data 
UPDATE products
SET title = :new_title,
    version = version + 1
WHERE product_id = :product_id
  AND version = :version_the_client_read;

-- 1 row changed: update accepted.
-- 0 rows changed: tell the client the record changed; reload/merge.

This compare-and-swap protects concurrent edits at the writer. It is not a substitute for authorization, validation, or a transaction when multiple rows must change together.

Interview check: name the authority, the allowed stale window, and the behavior when a replica is behind. “We have replicas” is not a consistency promise. Continue in replication and partitioning.

Topic 4 · SLOs and error budgets: translate reliability into product decisions

Why it matters: “high availability” is not measurable. An SLO names the user-visible journey, the indicator, the target, and the measurement window. It lets product and engineering make an explicit trade-off between shipping change and protecting reliability.

User journeyPlace a valid order
→
SLISuccessful eligible checkouts / eligible attempts
→
SLOFor example, 99.9% over 30 days
→
Error budgetAllowed unsuccessful fraction drives action

Worked example: with a 99.9% success target over a 30-day window, the allowed failure fraction is 0.1%. If measured as time-based availability, that is about 43.2 minutes in a 30-day month. For a request-based checkout SLI, calculate the budget from eligible attempts instead; do not convert it to downtime.

How to use it: define eligibility and exclusions before measuring (for example, separate invalid user input from server failures). Track latency as a distribution, not just an average; pair success with correctness, because a fast oversell is not a successful checkout. Alert on rapid budget burn and investigate slower trends. If the budget is being consumed too quickly, reduce risky releases, fix the dominant failure mode, and communicate the customer impact.

Useful signals: successful eligible journey rate · p95/p99 latency · saturation/queue age · duplicate-charge and oversell count · dependency timeout rate · recovery time. Each signal needs an owner, dashboard, alert threshold, and runbook action.

Do not do this: set an ambitious availability number without a measurement, treat every endpoint as equally important, or page on a metric that has no clear action. See operations and the full checklist.

Start here: the five building blocks

Imagine ordering a notebook from a small online shop. System design is deciding which parts of the shop's software are needed, what each part remembers, and how the parts behave when something goes wrong.

1. Client: the customer-facing app

A client is the website or mobile app a person uses. It displays products and sends requests. It is not trusted to decide the real price, stock, identity, or payment result because a user can change or replay what their device sends.

2. Server: the shop's decision maker

A server receives a request, checks permission and rules, talks to storage or other services, then returns a response. It is the authority for decisions like “is this customer allowed to see this order?”

3. Database: durable memory

A database remembers important facts after a server restarts: products, available stock, orders, and payment attempts. Pick it based on the facts and rules you must protect, not because a technology is fashionable.

4. API: an agreed conversation

An API is the request/response contract between the client and server. For example: “Here is my cart; please try to create one order.” The API specifies inputs, success, errors, authentication, and what a retry means.

5. Network: the unreliable road

Parts communicate over a network. A request can be delayed, lost, repeated, or receive a response after the caller gives up waiting. A timeout does not tell you whether the other side completed its work.

A shopper taps “Buy.” The phone sends a request to the server. The server checks the order rules and saves an order in a database. The phone waits for a response.

Try it: Which component is the client? Which is the durable memory? If the phone times out, do we know that no order was created?

Check your answer
The phone/app is the client; the database is durable memory. A timeout only means the phone did not receive a response in time. The server may already have saved the order, so a safe retry needs an idempotency key (introduced below).

Follow one real purchase before drawing the architecture

Scenario: Maya buys one blue notebook for $12.00 from seller Northstar. Shipping is $3.00 and tax is $1.20, so the total is $16.20. The example uses dollars for readability; a real service must calculate and store money in the currency's smallest unit, such as cents.

1 · Search
Maya searches “blue notebook.” The app asks the server; the server gets matching results from a search index. The index is a fast, rebuildable copy, not the final authority for price or stock.
2 · Add to cart
The cart stores the selected offer and quantity. It is a shopping intention, not a promise that the price or stock will stay unchanged.
3 · Start checkout
The app sends the cart version, shipping address ID, and a unique idempotency key. The server verifies that the address belongs to Maya and creates one durable pending order intent.
4 · Recheck facts
The server reads the current offer and recalculates the total. If the price changed, it asks Maya to accept the new total instead of silently charging more.
5 · Reserve stock
The inventory owner atomically checks that at least one notebook remains and reserves one for this order until a deadline. The reservation prevents competing checkouts from claiming the same unit.
6 · Ask for payment
The server sends $16.20 to the payment provider using a stable provider idempotency key. The system stores the provider's reference and state, not raw card data.
7 · Confirm and tell others
After the payment outcome is known, the order moves through a valid state transition. A durable event later tells fulfillment to ship and notifications to update Maya.
8 · Show status
The API returns the order ID and state. Maya can refresh the order page; the order record remains authoritative even if a notification is delayed.

Choice: one app and one relational database first

Choose: a single application with Catalog, Cart, Checkout, and Inventory modules, plus a managed relational database.

Why: this is a small team's easiest design to build and operate. One database transaction can safely record the order intent and its retry key. You can enforce constraints and inspect the whole order in one place.

Do not add yet: ten microservices, a distributed cache, a message broker, and a container orchestration platform. They create network failures and operational work before the product has evidence it needs them.

Choice: use a payment provider

Choose: a reputable provider's hosted/tokenized payment flow.

Why: handling card data yourself creates significant security and compliance responsibilities. A provider handles sensitive card entry and gives you a reference and payment status.

Still your responsibility: verify provider callbacks, match the order/amount/currency, deduplicate events, reconcile uncertain outcomes, and never trust a success page redirect alone.

Choice: keep images out of the database

Choose: object storage for image files and a CDN to deliver them close to shoppers. Keep only the image URL/metadata with the product.

Why: large files need different storage and delivery behavior than small transactional records. This reduces database load and speeds up product pages.

Choice: let search be slightly stale

Choose: a search index for text queries, updated shortly after product changes. Recheck price and inventory from authoritative records at checkout.

Why: searching every product in the order database is a poor fit for text ranking and facets. A small delay in search results is tolerable; selling a nonexistent item is not.

A reliable choice sequence

  1. Write the user-visible requirement and the business invariant.
  2. Estimate workload and identify the likely bottleneck; label uncertainty.
  3. Choose the simplest design that can meet the target with safety margin.
  4. List failure modes, ownership, operational effort, security, and cost.
  5. Define a test/metric and a threshold that proves the choice insufficient.
  6. Only then add a component or distribute a boundary; review the decision after evidence.

Example: should MarketSquare add Redis?

Evidence: product reads repeatedly execute the same expensive query and database read saturation violates browse p95. First checks: execution plan, missing/inefficient index, payload size, CDN eligibility, and request duplication.

Choose a cache if: repeated safe-to-stale reads remain expensive and cache key/freshness rules are clear. Start with: a bounded TTL for public product detail, miss coalescing, origin concurrency caps, and cache metrics.

Do not cache: final stock eligibility, payment result, or authorization as the source of truth. Revisit if: hit ratio is low, invalidations are unreliable, or cache loss overloads SQL; then fix query/workload or intentionally design a fallback.

Example: should we split checkout into a service?

Not because: the codebase is large or microservices are fashionable. Consider it when: checkout needs independent scaling/isolation, an accountable team owns it, contracts are stable, and the change addresses measured contention or release risk.

Before splitting: define order/inventory/payment data ownership, saga and outbox behavior, deployment/telemetry, migration, and rollback. If one relational transaction currently enforces an invariant, explain how the new boundary preserves it.

Example: SQL or NoSQL for a new app?

Start with SQL when: relationships, transactions, uniqueness, reporting, and evolving query needs are important. Choose a non-relational model when: access patterns/data shape are clear and its partition/consistency model directly solves a requirement.

Write the top five reads/writes first. If you cannot state query patterns, scale, consistency, and failure expectations, you are not ready to choose based on a benchmark or label.

Realistic scenario: a flash sale, one item left, and a payment timeout

It is 9:00 AM. A popular notebook goes on sale. The database says only one unit is available. Maya and Leo tap checkout at nearly the same time. Maya's payment is accepted by the provider, but the reply to MarketSquare is delayed. Her phone retries. The provider also sends the same callback twice.

9:00:00.001 · Maya
Checkout starts with key maya-checkout-abc. The server creates a pending order intent tied to Maya, the cart version, request hash, and key.
9:00:00.002 · Leo
Leo also starts checkout. He has a different key and a different order intent.
9:00:00.010 · Stock owner
Maya's conditional stock update succeeds: available quantity changes from 1 to 0 and a reservation is recorded for Maya's order. Leo's competing update affects zero rows. Leo is told the item is no longer available; he is not charged.
9:00:00.020 · Payment provider
The provider accepts Maya's $16.20 authorization. The network reply is delayed, so MarketSquare cannot yet tell if it succeeded.
9:00:00.500 · Maya retries
The app retries using the same idempotency key. MarketSquare returns the same pending order. It does not create another order or send a new payment request with a fresh identity.
9:00:02.000 · Reconciliation
MarketSquare queries the provider or waits for a verified callback. It records the authoritative result against the same order/payment attempt. Until then, the order remains explicitly pending.
9:00:03.000 · Duplicate callback
The provider delivers the same event again. A unique provider-event ID and valid state transition mean the second delivery has no second business effect.
9:00:04.000 · Finish
After confirmed authorization, the order becomes confirmed and fulfillment is notified. If payment is definitively declined, the reservation is released. If the outcome stays unknown, reconciliation keeps working rather than guessing.

How to protect the last item

A dangerous implementation reads quantity 1 in application code, then later writes quantity 0. Maya and Leo could both read 1 before either writes.

Safer: make the check and decrement one atomic database operation, scoped to the offer:

UPDATE offers
SET available_quantity = available_quantity - 1
WHERE offer_id = :offer_id
  AND available_quantity > 0;

If exactly one row changed, this request reserved one unit. If zero rows changed, there was no unit left. In production, record the reservation and its expiry in a transaction; release it safely if payment definitively fails or the reservation expires.

Why each guard exists

  • Idempotency key: same customer intent and retries map to one order.
  • Atomic stock update: competing requests cannot both claim the final unit.
  • Stable provider key: ambiguous network retries do not create a second charge.
  • Pending state: the application does not lie while the provider outcome is unknown.
  • Verified, deduplicated callback: an untrusted or repeated message cannot confirm or charge twice.
  • Reconciliation: missed callbacks or ambiguous outcomes can eventually be corrected.

Practice: what if the queue is down after payment?

Payment is confirmed, but the message broker is unavailable. Should MarketSquare cancel the order or tell Maya to pay again?

Check your answer
Neither. Persist the order transition and an outbox event together in the database transaction. A publisher retries sending the outbox event when the broker returns. Fulfillment may start late, so monitor outbox age and show a truthful order status. Do not lose the confirmed order or charge again just because event delivery is delayed.

1. A repeatable system-design method

System design is a sequence of evidence-based decisions, not a race to name technologies. Establish the problem and constraints before drawing boxes.

  1. Clarify the product: identify users, primary journeys, boundaries, and what is deliberately out of scope.
  2. Quantify quality: turn “fast” and “reliable” into latency, availability, durability, freshness, privacy, and recovery targets.
  3. Estimate workload: calculate approximate reads, writes, storage, and peak traffic; state every assumption.
  4. Define contracts and ownership: sketch APIs, domain invariants, and which component is authoritative for each fact.
  5. Draw the simplest architecture: trace the most important user flows through compute, storage, and dependencies.
  6. Stress the design: follow retries, duplicates, partial failures, hot keys, traffic spikes, and stale data.
  7. Explain trade-offs: say what you choose, what you give up, and what evidence would change the decision.
Interview habit: narrate assumptions and keep a visible list of open questions. A clear, appropriately scoped design is stronger than an unexplained collection of fashionable components.

  • Real-time/collaborative: chat, live presence, multiplayer; consider connection fan-out, ordering, and reconnect.

  • Integration-heavy: workflow across vendors; plan for timeouts, rate limits, retries, and reconciliation.

2. Define MarketSquare before designing it

The first version supports shoppers and sellers. It should make product discovery easy and a purchase trustworthy. Avoid designing every future feature on day one.

Functional requirements

  • Sellers create product offers with price and available quantity.
  • Shoppers browse, search, filter, and view product details.
  • Shoppers maintain a cart and submit an order with a delivery address.
  • The system reserves available stock, requests payment, and reports order status.
  • Shoppers can cancel eligible orders, request refunds, and track fulfillment.
  • Sellers fulfill orders; notifications communicate material status changes.

First release boundaries

  • One currency and a limited shipping region; one external payment provider.
  • No live auctions, warehouse robotics, recommendation ML, or multi-region active-active writes.
  • Simple seller tools and rule-based search; expand only when validated.
  • Use a payment provider; do not store raw card numbers or security codes.

A boundary is a design input, not a claim that the omitted feature is unimportant.

Quality requirements (initial targets)

  • Product browse/search p95 under 300 ms for application responses in the launch region.
  • Order submission p95 under 1 s to acknowledge durable acceptance, excluding provider authentication.
  • 99.9% monthly availability for browse and order APIs, measured separately.
  • No duplicate order or charge when a client safely retries the same checkout request.
  • Accepted orders survive a single server or availability-zone failure.
  • Search may be briefly stale; confirmed orders and stock invariants may not be silently lost.

Prioritize invariants

Order: one customer intent creates at most one logical order. Inventory: reserved plus sold quantity never exceeds sellable stock. Payment: retries reuse a stable provider idempotency key and every result is reconciled.

These constraints influence the database, API behavior, event processing, and recovery plan—not just the checkout endpoint.

Little's Law: estimate in-flight work

For a stable system, in-flight requests ≈ arrival rate × average time in system. If 11,500 requests/second arrive and average response time is 0.25 seconds, roughly 2,875 requests are in flight across the system.

This estimates concurrency, not the number of servers by itself. Size instances by tested per-instance capacity and keep headroom for variance, deployments, and a zone failure. Tail latency can grow sharply near saturation.

Turn data volume into a retention estimate

If 40,000 orders/day average 20 KB of order/line metadata, raw growth is about 800 MB/day or 292 GB/year before indexes, replicas, backups, and logs. A 3-year online history is about 876 GB raw.

State which bytes are included, retention window, growth, indexes, and redundancy. Media is separate and often much larger. This calculation informs storage/partition/archive planning—not a direct disk purchase number.

Estimate queue drain time

If a backlog contains 120,000 fulfillment events and healthy workers complete 800 events/second, ideal drain time is 150 seconds. If new events arrive at 500/second during recovery, net drain rate is 300/second, so the backlog takes about 400 seconds to clear.

Include retries, uneven work, downstream quotas, and poison messages; measure actual completion rate. More workers help only if the downstream can accept the added work.

Translate estimates into a capacity plan

  1. Separate browse, search, cart, checkout, seller, and background work.
  2. Estimate average and peak requests for each; include burst duration and read/write mix.
  3. Estimate payload, database operations per request, cache hit rate, and external-provider quotas.
  4. Benchmark one instance/partition with realistic data; derive safe capacity below saturation.
  5. Plan for N-1 failure (lose one instance/zone) and a controlled overload response.
Always label the estimate: DAU is not concurrency; average RPS is not peak RPS; storage bytes are not provisioned disk. Show the formula, assumptions, and likely range. Refine only the estimates that could change the architecture.

7. Walk the two critical flows

Browse and search (read-heavy)

  1. Client sends a bounded, authenticated or anonymous query through edge protection.
  2. API checks a cache for safe, public product data; use cache keys that include locale/currency where relevant.
  3. On a miss, Search reads its index and returns a small page of product/offer summaries.
  4. Detail views fetch authoritative current price/availability as needed; media comes from object storage/CDN.
  5. Catalog/offer updates publish changes; indexers update the search projection asynchronously.

Trade-off: search can be briefly stale. Clearly distinguish displayed estimates from final checkout validation.

Checkout (correctness-critical)

  1. Validate identity, cart version, address, and idempotency key; create or return the existing order intent.
  2. Recheck current price and atomically reserve inventory with a bounded expiry.
  3. Request payment authorization using a stable provider idempotency key.
  4. Persist the outcome and order transition; publish an event through a transactional outbox.
  5. Capture/confirm according to the agreed payment policy; fulfillment consumes the confirmed-order event.
  6. On failure, release reservation, void/refund as appropriate, and expose an explicit final or pending state.

Never infer success from a timeout. Query provider status or reconcile asynchronously before retrying an ambiguous payment outcome.

8. Scale and improve performance where needed

Stateless compute

Keep request handlers replaceable; store sessions and durable state outside instances. Scale horizontally behind a load balancer. Bound connection pools and per-request work.

Caching

Cache public, frequently read product data with a TTL and version/invalidation strategy. Use request coalescing and origin limits against cache stampedes. Never make cache the only copy of an order or stock fact.

Database scaling

Measure query plans and indexes first. Add read replicas for suitable stale-tolerant reads. Partition/shard only after measuring limits; choose keys that distribute load without breaking needed transactions.

Async workloads

Queue emails, indexing, and fulfillment work to absorb bursts. Bound queue depth/age, autoscale consumers, apply backpressure, and isolate critical checkout from noncritical work.

Hot keys and oversell

One popular offer may concentrate reads or writes. Cache reads, rate-limit abusive callers, and serialize or atomically condition stock updates at the stock owner. Do not rely on a stale cache decrement for correctness.

Search and media

Keep large images out of application responses; use object storage, responsive formats, and CDN. Search projections can be rebuilt from durable product/offer changes.

Capacity is a system: database connection limits, downstream rate limits, queue consumers, cache memory, and egress can become the bottleneck before CPU. Scale the constrained dependency, not just the web tier.

Failures are expected: a dependency can be slow, unavailable, or return an ambiguous response while the rest of the system is healthy. Make behavior explicit.

Resilience building blocks

  • Timeout every remote call; retry only transient errors and only when safe.
  • Use exponential backoff with jitter, bounded attempts, and an overall deadline.
  • Use circuit breakers, bulkheads, quotas, and backpressure to contain failure.
  • Send poison messages to a monitored dead-letter queue; repair and replay deliberately.
  • Use health checks and graceful shutdown so deploys do not abandon in-flight work.

Consistency by business need

Strong/transactional: inventory reservation, order transitions, idempotency records. Eventually consistent: search, analytics, notifications, and many read models.

Show freshness where users need it; design for duplicate and out-of-order events. A queue provides delivery mechanics, not automatic exactly-once business behavior.

10. Security, privacy, and abuse prevention

Identity & authorization

Use a trusted identity provider. Enforce object-level authorization on every order, address, cart, and seller resource. Separate shopper, seller, support, and admin permissions.

Protect data

Use TLS in transit, managed encryption at rest, secret rotation, least-privilege service identities, and audited access. Minimize personal data and define retention/deletion rules.

Payment boundary

Use provider-hosted or tokenized payment methods; never log payment secrets or raw card data. Verify signed webhooks, amount/currency/order match, replay handling, and provider idempotency.

Abuse and application safety

Validate input; protect against injection, CSRF, XSS, SSRF, credential stuffing, scraping, bots, and denial-of-service. Apply rate limits, fraud signals, safe output encoding, and security testing.

Security is a cross-cutting requirement: include threat modeling, dependency/image scanning, audit logs, incident response, and compliance scope in delivery and operations.

11. Operate, observe, test, and evolve the system

Observability

  • Metrics: request rate, error rate, latency percentiles, saturation, queue age, outbox lag, and payment pending age.
  • Logs: structured, access-controlled, useful for diagnosis, with secrets and sensitive personal data excluded.
  • Traces: correlation IDs across API, database boundaries, broker, consumers, and payment adapter.
  • Business signals: checkout success, oversell incidents, duplicate suppression, refund time, and shipment delay.

Service objectives

Define separate SLOs for browse, search, order acceptance, and payment completion. An error budget makes the reliability-versus-release-speed trade-off visible. Alert on user impact and fast error-budget burn, not every exception.

Write runbooks with owner, customer impact, safe mitigations, escalation, and recovery verification.

Testing strategy

  • Unit tests for pricing, state transitions, and reservation invariants.
  • Integration/contract tests for database, broker, identity, and payment adapter.
  • End-to-end tests for browse-to-order, retry, cancellation, refund, and seller flows.
  • Load, soak, failover, restore, and fault-injection tests at realistic boundaries.
  • Security, authorization, privacy, and migration compatibility tests.

Deploy and change data safely

Build immutable artifacts, scan dependencies, and promote the same artifact through environments. Use canary/gradual rollout and automatic rollback signals. Evolve schemas with expand → deploy → backfill → contract so old and new application versions coexist.

Disaster recovery

Set recovery time objective (RTO) and recovery point objective (RPO) per domain. Backups are not proven until restored. Regularly rehearse zone/regional recovery, credential loss, event replay, and payment/order reconciliation.

Cost and operational complexity

Track cost per order, storage growth, egress, idle capacity, logs, and managed-service minimums. Choose caches, replicas, multi-region, and extra services when their measured user or risk benefit justifies the ongoing cost.

Deep dive 1: trace a request across the network

The network is not an invisible, reliable wire. It has name lookup, connection setup, encryption, routing, queues, timeouts, retries, and independent failure points. Trace these before claiming an API is “fast.”

1 · DNS
The device asks DNS for the site's address. A cached answer avoids repeat lookup; TTL controls how long it may remain cached. DNS changes are not an instant failover switch because resolvers cache results.
2 · TLS connection
The client establishes an encrypted HTTPS connection and validates the server certificate. Connection reuse avoids repeating TCP/TLS setup for every API call.
3 · Edge
CDN serves cacheable media/public content. WAF and DDoS controls filter abusive traffic. The edge must not cache personalized order data under a shared key.
4 · Load balancer / gateway
Traffic is routed to a healthy application instance. The gateway may authenticate, enforce quotas, and route versions; business ownership checks still belong in the application.
5 · Application
The service validates input and permission, runs bounded work, and calls dependencies over their own network connections. Each call needs a timeout that fits within the caller's remaining deadline.
6 · Storage / dependency
The database returns a result or error; the application maps it to a stable API response, logs a correlation ID, and returns it over the encrypted connection.

Latency budget: add the waits, not just CPU

Suppose the product-page API target is 300 ms p95. A request may spend 35 ms at the edge/network, 20 ms in gateway/auth, 35 ms in application work, 90 ms in search, 45 ms in a product lookup, and 30 ms returning/rendering. The total is 255 ms; only 45 ms remains for variability and queues.

These are example allocations, not universal targets. Measure percentiles in the real path. Sequential calls add latency; parallel calls take approximately the slowest call, but consume resources and complicate partial failures.

Deadlines, timeouts, retries, and overload

  • Give the whole request a deadline; pass only the remaining time to each dependency.
  • Set connect and response timeouts. A timeout bounds waiting; it does not cancel a remote side effect unless that system confirms cancellation.
  • Retry only transient errors and idempotent operations, with capped exponential backoff and jitter.
  • Retries amplify load during an outage. Bound attempts and total retry budget; return an explicit retryable error when exhausted.
  • Use connection pools and limits. Unbounded connection creation can exhaust the database even while application CPU looks healthy.
Example: if checkout has a 2-second overall deadline and stock reservation already consumed 1.4 seconds, do not start a new 1-second payment attempt and pretend the whole request can finish on time. Persist a pending state and continue safely in the background if that is the chosen contract.

Deep dive 2: database transactions, indexes, and safe writes

A database is not just a place to save JSON. Its keys, constraints, transactions, indexes, and isolation rules determine whether concurrent shoppers can violate business invariants.

Relational model and constraints

Use stable IDs and foreign keys for relationships; store money as integer minor units plus ISO currency; use UTC timestamps; define uniqueness and non-null rules in the database, not only in application code.

orders(
  order_id, customer_id, status,
  currency, total_minor, created_at
)
order_lines(
  order_id, line_number, offer_id,
  seller_id, product_name_snapshot,
  quantity, unit_price_minor
)
reservations(
  reservation_id, order_id, offer_id,
  quantity, expires_at, state
)

Snapshot what the customer agreed to buy. A product title or price edit tomorrow must not change yesterday's receipt.

ACID in the marketplace

  • Atomicity: either the database transaction's related order rows and outbox row commit together, or none do.
  • Consistency: declared constraints/invariants hold before and after each committed transaction.
  • Isolation: concurrent transactions do not expose an unsafe intermediate state; exact guarantees depend on isolation level.
  • Durability: acknowledged commits survive the failures covered by the database's durability configuration.

ACID applies within the database transaction. It does not atomically include an external payment provider or email system.

The race: read, then write is unsafe

Unsafe sequence: Maya reads stock = 1; Leo reads stock = 1; Maya writes 0; Leo writes 0. Both may believe they bought the same item. Use a single conditional update or a correctly locked transaction, then verify affected row count.

BEGIN;
UPDATE offers
SET available_quantity = available_quantity - :qty
WHERE offer_id = :offer_id
  AND available_quantity >= :qty;
-- Continue only if exactly one row changed.
INSERT INTO reservations (...);
COMMIT;

Production code also checks offer state, reservation expiry, duplicate order identity, and transaction rollback. Define a consistent lock/update order to reduce deadlocks.

Isolation and retry behavior

At weaker isolation, two valid reads can still lead to a write conflict. Serializable isolation may abort one transaction; the application must retry the entire transaction with bounded attempts and safe inputs. Deadlocks are expected concurrency outcomes, not proof of database corruption.

Never retry only the last statement if earlier statements in the transaction must be repeated as one unit. Never repeat an external charge inside a database transaction retry without provider idempotency.

Indexes: faster reads, more write work

An index is an auxiliary ordered lookup structure. For GET /orders/{id}, the primary key is usually right. For a seller's recent orders, a composite index might start with (seller_id, created_at DESC) because queries filter by seller and sort by time.

Indexes consume storage and slow inserts/updates. Use query plans and production-like data to verify selectivity; do not index every column. A query that returns half the table may be faster as a scan.

Pagination and data growth

Offset pagination (OFFSET 100000) can scan and discard many rows and can shift as new orders arrive. Keyset pagination uses a stable ordered cursor, such as (created_at, order_id), and a next-page condition. Sign or validate cursors; never trust a cursor to grant access.

Define retention, archive rules, backup/restore expectations, and deletion policies before large history accumulates.

Deep dive 3: design APIs clients can safely depend on

An API is a versioned promise, not just a URL. Define who may call it, the meaning of each operation, how errors and retries behave, and how the contract evolves while old clients remain in use.

Choose a communication style for the client

  • REST/HTTP + JSON: good default for public web/mobile resource APIs; widely understood, cacheable for suitable GETs, easy to inspect.
  • GraphQL: useful when clients need flexible selection across related data; requires query depth/cost limits, authorization on every field, and caching strategy.
  • gRPC / typed RPC: efficient typed service-to-service contracts and streaming; browser support/proxies and public-client ergonomics may need extra layers.
  • WebSocket / server-sent events: useful for live order updates; connections need authentication, reconnect, fan-out capacity, and polling fallback.

These are not mutually exclusive across the whole system. Start with the simplest protocol that serves the consumer and operational needs.

Authentication is not authorization

Authentication asks “who is calling?” Authorization asks “may this caller perform this action on this specific resource?” A valid token does not permit Maya to read Leo's order.

Verify issuer, audience, signature, expiration, and required claims. Enforce customer/seller ownership on the server for every object access. Do not trust client-supplied user IDs, seller IDs, price, role, or status.

HTTP semantics and safe retries

GET should not change business state; PUT commonly replaces a known resource state; POST commonly creates an action/resource. These conventions help clients, caches, and retries but are not a substitute for a precise contract.

Use idempotency keys for retryable create/payment actions. Persist key + authenticated principal + canonical request hash + outcome. Same key/same request returns the prior outcome; same key/different request returns conflict. Define expiry longer than the real retry/reconciliation window.

Errors and asynchronous outcomes

Return a stable error code, safe human-readable message, correlation ID, and retry guidance. Distinguish invalid input, unauthenticated, forbidden, conflict/out-of-stock, rate-limited, dependency unavailable, and unknown/pending results.

Use 202 Accepted only when work is durably accepted for later completion; return an operation/order resource the client can query. A generic timeout response must not imply “nothing happened.”

Compatibility and versioning

Prefer compatible additions: optional fields, tolerant readers, documented defaults. Do not silently change a field's meaning or remove it while clients still use it. Use explicit API versions for breaking changes, monitor old-version traffic, publish migration windows, then retire safely.

For event/API schema evolution, test old consumer with new producer and new consumer with old payload where rollout order requires it.

Pagination, filtering, and abuse limits

Bound page size, query length, sort choices, filter count, and response bytes. Cursor pagination should encode the stable sort position and relevant query context; validate/sign it and still enforce authorization.

Rate-limit by authenticated identity, IP/device signals, and expensive operation. Return 429 with a retry hint where appropriate; do not make a client retry sooner than the service can recover.

Deep dive 4: gateways, load balancing, and traffic protection

Load balancer and health checks

A load balancer distributes requests across application instances. Round-robin is simple; least-connections can help uneven request durations; consistent hashing can keep related keys near a cache but risks hot spots. Use the strategy that matches workload and failure behavior.

Liveness asks “should this process be restarted?” Readiness asks “should it receive traffic now?” A process can be alive but not ready because it is draining or lacks a required dependency. Avoid health checks that restart every instance just because an optional service is down.

Gateway versus service responsibility

Gateway responsibilities fit shared edge concerns: TLS termination, request size limits, coarse authentication, routing, quotas, and request IDs. Domain services still own order rules, resource authorization, pricing, and state transitions.

A backend-for-frontend can tailor a response to a mobile/web client, but avoid duplicating business rules in each client-specific layer.

Rate limiting: token bucket example

A token bucket refills at a fixed rate up to a capacity. Each request consumes tokens. A bucket of 20 tokens refilling at 5/second permits a short burst of 20, then sustains about 5 requests/second.

Use separate limits for search, login, checkout, and seller writes. Decide key (account, IP, tenant), burst, refill rate, distributed-counter consistency, and behavior if the limiter is unavailable. Rate limits protect capacity; fraud controls decide whether behavior is suspicious.

Admission control and backpressure

When checkout or a provider is saturated, accepting unlimited work only creates timeouts and retry storms. Bound concurrent work and queue length. Reject excess work early with a clear retry response, or durably accept it only if the product supports a pending workflow.

Prioritize critical order/payment work over recommendations or analytics. Degrade optional features (personalized ranking, rich facets) before the core purchase path.

Autoscaling: signals and lag

CPU alone misses I/O waits and queue backlogs. Scale app instances using a combination of request concurrency/latency and resource saturation; scale consumers using queue age/lag and drain capacity. Account for startup delay and downstream limits to avoid oscillation.

Never autoscale beyond database connection or payment-provider capacity. A scaling policy needs a maximum, a cooldown, and a safe overload behavior.

Protect the origin

Use CDN for cacheable public product media, WAF/DDoS controls at the edge, request size/time limits, per-tenant quotas, and bounded cache-miss concurrency. Cache keys must include every representation dimension such as locale/currency and must exclude secrets.

Deep dive 5: replication, partitioning, consistency, and CAP

One database machine has finite capacity and can fail. Distributed data improves capacity or availability, but copies can disagree temporarily and partitions make communication uncertain. Pick an explicit consistency promise for each domain fact.

Replication: copies for reads and recovery

A primary accepts writes and replicates a log to followers. Synchronous replication waits for selected followers before acknowledging; this can reduce data loss but add latency or make writes unavailable when a required follower is unreachable. Asynchronous replication responds sooner but can lose recent acknowledged data on failover, depending on configuration.

A read replica may lag. If Maya updates her address and immediately reads it from a lagging replica, she may see the old address. Use primary reads, session stickiness/read-your-writes, or a bounded-staleness policy for such flows. Search and analytics usually tolerate lag; checkout's stock decision generally should not rely on a stale replica.

Partitioning / sharding: split ownership

Choose a partition key that spreads traffic and data while keeping common operations local. customer_id can colocate carts/orders for one customer, but a celebrity seller or global inventory item can create hot partitions. offer_id helps inventory ownership but may complicate multi-offer orders.

  • Range partitions support ranges and retention but can hotspot at the newest end.
  • Hash partitions distribute keys but make range queries and rebalancing less direct.
  • Directory/lookup partitioning permits movement but adds a mapping service.

Cross-shard joins and transactions are expensive. Define how to add partitions, move data, dual-read/dual-write safely, and roll back a migration.

Consistency levels in human terms

  • Strong/linearizable read: a successful read behaves as if it occurred after the latest completed write in one order.
  • Read-your-writes: a customer sees their own recent change even if other reads may be stale.
  • Eventual consistency: replicas/projections may differ temporarily but converge if updates stop and replication recovers.
  • Monotonic read: a session should not see a newer value and then move backward to an older one.

Choose by user-visible invariant: stock/order/payment needs stronger guarantees; recommendations/search can normally be eventual.

CAP is about a network partition

When nodes cannot communicate, a distributed data operation cannot always guarantee both linearizable consistency and a successful response from every reachable side. For the affected operation, decide whether to reject/wait (preserve consistency) or accept possibly conflicting data (favor availability) during the partition.

CAP is not a permanent menu where every database is simply “CP” or “AP.” Latency, failure detection, quorum, recovery, and operation type matter. For orders, prefer not to double-sell; for anonymous view counts, accepting temporary divergence may be fine.

Quorums and failover

Some replicated systems read/write a quorum of replicas. Quorum overlap can provide useful guarantees only under the system's assumptions; it does not automatically make arbitrary multi-row workflows serializable. Understand replica count, quorum size, failure domains, and whether a failover can promote a node missing writes.

Failover requires fencing the old primary to prevent two writers (split brain), selecting a sufficiently current replica, updating routing, and reconciling in-flight requests.

Multi-region: choose ownership before topology

Start with one write-owning region and replicated disaster recovery if that meets RTO/RPO. For active-active writes, define data ownership (for example, home region per customer/order), conflict resolution, inventory reservation authority, payment reconciliation, and what happens when regions are partitioned.

Global synchronous writes add inter-region latency. Independent regional stock pools can prevent oversell but may strand inventory; a global stock counter increases coordination. State the business trade-off explicitly.

Practical decision: keep each offer's stock reservation under one authoritative writer/partition. Read product descriptions from replicas or cache if useful, but do not let disconnected regions each sell the same final unit unless inventory was deliberately allocated to them in advance.

Deep dive 6: caching, queues, streams, and event correctness

Cache-aside, step by step

  1. Application checks cache key product:{id}:{locale}.
  2. On hit, return the value only if its authorization and freshness rules fit the request.
  3. On miss, read the source of truth, populate cache with a bounded TTL, then return.
  4. On product update, invalidate/version the key or accept documented TTL staleness.

Use a cache for repeated, recomputable reads—not the only durable order or inventory record. Decide behavior on cache outage (fallback, degrade, or reject) and protect the database from a sudden miss storm.

Cache failure patterns and remedies

  • Stampede: many misses hit the database together. Coalesce same-key loads, add jitter, or refresh proactively.
  • Hot key: one item dominates requests. Replicate/cache safely, rate-limit, or serve a bounded stale public view.
  • Stale overwrite: slow old read repopulates after a newer write. Use versions/fencing or compare-and-set.
  • Invalidation race: eviction happens before a concurrent old read writes stale data back. Versioned keys or coordinated update patterns reduce it.
  • Cache outage: fallback can overload the database. Apply origin concurrency limits and graceful degradation.

Queue versus event stream

A work queue assigns a task to a worker; after successful acknowledgment, the task is usually removed. A retained event stream stores an ordered log per partition that multiple consumer groups can replay independently. Choose based on whether you need task distribution or retained independent history, replay, and fan-out.

Neither guarantees exactly-once business effects across databases and external providers. Design consumers to be idempotent and monitor lag/age.

Outbox closes the database/broker gap

Danger: commit an order, then crash before publishing OrderConfirmed; or publish before the transaction rolls back. In one database transaction, write both the order change and an outbox row. A publisher sends pending rows and marks them delivered. A crash can publish twice, so consumers deduplicate by event/business ID.

Monitor oldest pending event, retry count, and dead-letter volume. Define retention, poison-event repair, and safe replay procedures.

Ordering, schemas, and event evolution

Ordering is normally guaranteed only within a partition/key, not across the whole broker. Key order events by order ID when per-order sequence matters. Include event ID, aggregate ID, sequence/version, occurred time, schema version, and trace context.

Consumers should tolerate additive optional fields and unknown event versions; breaking changes require a migration plan. Event time and arrival time differ; do not assume events arrive in business order.

Delivery guarantees in practical terms

At-most-once: may lose work, no redelivery. At-least-once: work is retried and may appear multiple times. Common systems choose at-least-once plus idempotent handling.

A consumer can save a unique event ID and its business effect in one local transaction. For an external email/payment API, use its idempotency support where available and retain a reconciliation path.

Deep dive 7: deploy a production system and recover it

Reference deployment topology

For the first production region: public DNS → CDN/WAF → load balancer → at least two stateless app instances across separate availability zones → managed relational database with backups and multi-zone durability appropriate to the target → object storage/CDN for media. Keep databases, broker, and internal services off the public internet.

Use separate development, test, staging, and production environments; separate identities and secrets; private networking where appropriate; and infrastructure-as-code for repeatable changes. Exact cloud products depend on requirements, region, skills, and cost.

Release safely

  1. Build one immutable artifact; scan dependencies and generate provenance.
  2. Run unit, integration, contract, migration, and security checks.
  3. Deploy a backward-compatible database expansion first.
  4. Canary a small traffic slice; compare error, latency, and business metrics.
  5. Gradually roll out; stop/roll back automatically on agreed thresholds.
  6. Backfill data, verify, then remove old schema only after old code is gone.

Rollback application code does not automatically roll back a destructive database migration. Design migrations to coexist across versions.

Availability math and error budgets

For a 30-day month, 99.9% availability permits roughly 43.2 minutes of unavailable time; 99.99% permits roughly 4.32 minutes. These figures assume the agreed measurement window and definition. A request-based SLI can better reflect user impact than “server process is running.”

Define good requests, denominator, exclusions, window, and owner. If the error budget is being consumed too fast, prioritize reliability work and slow risky releases.

RTO, RPO, backup, restore

RTO: maximum acceptable time to restore service. RPO: maximum acceptable lost-write window. For example, a 30-minute RPO means recovery may lose up to 30 minutes of changes; that may be unacceptable for confirmed orders.

Choose backup frequency, point-in-time recovery, replica/failover behavior, and cross-region copies to meet the agreed targets. Regularly restore into an isolated environment, verify counts/consistency, and rehearse who declares failover and how writes resume.

Active-passive versus active-active

Active-passive: one region serves writes; a standby is promoted during disaster. Simpler ownership, but recovery takes time and replication may lag. Active-active: several regions serve traffic/write; lower regional latency and potential availability, but requires conflict/ownership strategy, global coordination, and more complex testing.

Use active-active only when latency/availability requirements justify its consistency and operations cost. A DNS switch alone does not solve data conflicts or prevent split brain.

Scale tests and capacity headroom

Test expected peak and a defined burst above peak, including database connections, cache miss behavior, queue backlog drain rate, and provider limits. Keep headroom for failover: if a region/zone is lost, surviving capacity must carry the required load or the product must degrade intentionally.

Track capacity per bottleneck and repeat tests after material schema, workload, or dependency changes.

Advanced HLD: design for evolution, ownership, and blast radius

At senior level, the diagram is only a hypothesis. Explain why boundaries exist, which team or component owns each business fact, what can fail independently, and how the design evolves without a risky rewrite.

Boundaries follow invariants and change

Group behavior that changes together and must uphold the same rules. In MarketSquare, order lifecycle and inventory reservation may begin in one modular application because checkout needs a short, reliable local transaction. Search indexing and notifications are separate asynchronous concerns because they can lag without changing whether an order is valid.

Split a module into a service when independent scaling, ownership, release cadence, isolation, or compliance is worth the cost of network calls, duplicated data, retries, and operations. Keep the data owner explicit; avoid two services both believing they own the final order status.

HLD is also a failure-domain design

Draw zones, regions, databases, brokers, caches, identity, payment, and their dependencies. For each dependency ask: Is it required synchronously? What is the timeout/deadline? What happens on partial failure? Can the caller shed load, serve stale data, queue work, or fail closed?

Separate critical checkout capacity from optional recommendations and analytics with bulkheads and quotas. A shared database, cache, network path, or credential can still couple otherwise separate services; identify these hidden shared failure domains.

Choose data topology from ownership

Keep one authoritative writer for each invariant wherever possible. Orders, payment attempts, and inventory reservations need durable ownership and audit history. Search, recommendations, and seller dashboards can be projections rebuilt from source events.

When introducing a new store, define how it is populated, how lag is measured, how it is rebuilt, and what users see while it is stale. Do not dual-write two databases in a request and assume both succeed together.

Multi-region by data class, not slogan

Global product reads and media can often be served close to the shopper. A single order or inventory key still needs a clear write owner, such as a home region or partition leader. Route writes consistently, make failover fencing explicit, and reconcile uncertain writes before accepting conflicting ownership.

Measure regional latency and recovery needs first. Active-active writes introduce conflict resolution, duplicate work, global coordination, and operational drills; active-passive may meet the target with simpler business semantics.

Evolution path: strangler, not big bang

  1. Extract a stable domain contract from the modular monolith.
  2. Move one capability behind that contract while retaining one source of truth.
  3. Use an outbox/CDC or controlled backfill to build the new read model.
  4. Compare old and new results in shadow mode; do not double-apply side effects.
  5. Route a small cohort, monitor business invariants, then expand and retire old code.

Plan rollback and data compatibility before cutover. A service split is incomplete until ownership, alerts, on-call, deploy, recovery, and cost are also owned.

Make architecture decisions reviewable

Record the context, constraints, options, chosen decision, consequences, owner, and revisit trigger. Example: “Keep inventory writes in the relational primary until conditional-update contention or database saturation violates checkout SLO; then test per-SKU serialization/partition ownership.” This gives future teams evidence rather than folklore.

Senior design test: for every new box, name the requirement it serves, the new failure mode it creates, the team that owns it, the metric that proves it works, and the simpler alternative you rejected.

Advanced capacity: traffic changes shape, not just size

“10× traffic” is underspecified. A mature design distinguishes average from peak, reads from writes, hot keys from uniform load, steady growth from sudden bursts, and legitimate demand from retry or bot amplification.

Classify the workload before scaling

  • Rate: requests/second, concurrent requests, and bytes/second by endpoint.
  • Shape: daily seasonality, campaign burst, ramp rate, duration, and recovery tail.
  • Mix: browse/search/cache hit, cart writes, checkout, seller updates, background jobs.
  • Distribution: top product/SKU, seller/tenant, geography, client version, and query complexity.
  • Amplification: retries, fan-out calls, cache misses, webhook redelivery, and bot traffic.

Segment telemetry by route and business operation. Averages hide hot partitions and p99 pain; track request volume, concurrency, latency percentiles, errors, and saturation together.

Quick capacity math and its limits

requests/second ≈ daily requests ÷ 86,400 × peak factor. If 8.64 million daily browse requests have a 5× peak factor, the estimated peak is 500 requests/second. If each request fans out to 4 services, that is roughly 2,000 downstream calls/second before retries.

Little’s Law gives in-flight work L = arrival rate λ × average time W. At 500 requests/second and 200 ms average service time, expect about 100 in-flight requests at that boundary. This estimates concurrency, not safe capacity; load-test saturation, queueing, tail latency, and dependency limits.

Traffic-shift scenarios and response

  • Campaign surge: prewarm safe catalog/media data, reserve checkout/provider capacity, gradually admit traffic, and use a waiting room only if product rules permit.
  • Hot SKU: edge/cache reads, bound per-key concurrency, and serialize/atomically condition writes at the inventory owner.
  • Read-to-write shift: protect database write capacity; a read replica does not help a saturated primary's writes.
  • Regional shift: verify regional cache warmth, data ownership, provider reachability, and failover headroom before routing.
  • Retry storm: honor deadlines, use jitter and retry budgets, and stop retries at the layer that knows whether the operation is safe.

Queue stability and drain time

If work arrives faster than consumers complete it, backlog grows even when workers are “healthy.” At arrival rate λ and completion rate μ, sustained stability requires total completion capacity above arrival rate, with headroom for variance and failures.

Drain-time estimate: backlog ÷ (completion rate − arrival rate), when completion exceeds arrival. For example, 60,000 tasks, 800 completed/second, and 500 arriving/second take about 200 seconds to drain under those simplified steady rates. Check provider quotas, partition limits, poison messages, and downstream capacity before adding consumers.

Autoscale the constrained resource

Scale API instances on concurrency/latency and saturation; workers on oldest-message age and drain capacity; databases through query/index/write efficiency and connection limits. Scaling a stateless tier can make an overloaded database fail faster.

Include startup delay, warm-up, cooldown, maximum capacity, connection-pool budgets, and graceful scale-in. Keep emergency load shedding and feature degradation ready before the event.

Capacity plan as an experiment

Test baseline, expected peak, burst, soak, dependency degradation, and zone loss. Validate p95/p99 latency, checkout correctness, cache behavior, DB lock/connection pressure, queue age, provider throttling, and recovery time. Record assumptions and repeat after code, schema, traffic mix, or dependency changes.

Advanced caching: freshness, correctness, and failure under load

A cache is a performance optimization with its own data model and failure modes. Define what may be stale, for how long, who invalidates it, and how the system behaves when the cache is empty, slow, full, or unavailable.

Choose cache layers by content and control

Browser/CDN: public images and cacheable catalog representations close to users. Application cache: process-local immutable/configuration data with short lifetime. Distributed cache: shared product/query results or computed reference data. Database buffer/index: still benefits from query and access-pattern design.

Each layer has different invalidation, privacy, eviction, and observability behavior. A cache hit at one layer does not prove the source is healthy or the data is correct.

Design keys as part of the contract

Use a stable namespace and include every value that changes the representation: product:v3:{productId}:{locale}:{currency}:{visibility}. Include schema/representation version to prevent old serialized values being interpreted as new. Do not put credentials or sensitive personal data into shared keys.

For search, include normalized query, filters, sort, page/cursor, locale, currency, and personalization segment if applicable. Bound key length/cardinality and protect against attacker-controlled cache pollution.

Freshness strategies and their promises

  • TTL: simple bound on staleness; randomize expiry to spread load.
  • Invalidate on write: fast freshness when events arrive, but missed invalidations need a repair path.
  • Versioned keys: publish a new version/pointer; avoids deleting every related key but requires version coordination.
  • Stale-while-revalidate: return bounded stale data while one refresh runs; good for catalog, not authoritative checkout decisions.
  • Negative caching: briefly cache “not found” to protect origin; invalidate carefully when an item is created.

State the freshness SLA per field. A product description can be briefly stale; final price, authorization, and stock eligibility must be revalidated by their authoritative owner during checkout.

Prevent stampedes and hot-key overload

When a hot key expires, thousands of callers can miss together. Use request coalescing/single-flight, TTL jitter, early refresh, bounded origin concurrency, and controlled warm-up. For very hot public data, edge caching or replicated read paths may help.

Sharding does not fix a single hot key if every request maps to one shard. Consider safe replication, key-space spreading, or controlled serialization for reads; never split an authoritative stock invariant into independent counters without a correctness protocol.

Cache-aside race and stale resurrection

Classic flow: read cache; on miss read database; populate cache. Race: reader loads old value, writer commits new value and deletes key, then reader writes the old value back. Mitigate with versioned values/keys, compare-and-set, short TTLs, or a cache fill protocol tied to source version.

Invalidation events can be duplicated or arrive out of order. Attach entity version/update sequence and only replace a cached value with a newer version. Reconcile or rebuild when event lag exceeds the freshness promise.

Fail open or fail closed—decide per data

If product recommendations cache is down, omit recommendations or use a safe default. If authorization or inventory cache is uncertain, consult the source of truth or reject/defer the sensitive action; do not treat cache absence as permission or stock availability.

Protect the origin during cache outage with concurrency limits, circuit breakers, stale-safe responses, admission control, and explicit fallback behavior. Monitor hit ratio alongside origin load, cache latency, evictions, memory, hot keys, and staleness—not as a single success metric.

Advanced LLD: turn the design into safe code

Low-level design makes responsibilities, contracts, state transitions, and concurrency explicit. A senior answer is not a class-name list: it shows where invariants are enforced, how races are prevented, and how the behavior can be tested and changed safely.

Model domain behavior, not just tables

Define aggregates around consistency boundaries. An Order owns its allowed lifecycle transitions; an InventoryItem or reservation owner enforces available/reserved quantities; a PaymentAttempt records provider interaction and uncertainty. Keep money in integer minor units plus currency, and snapshot purchased SKU, title, quantity, and unit price on the order line so catalog edits do not rewrite history.

Separate commands (“reserve stock”) from queries (“show stock hint”). Keep entities responsible for valid transitions and application services responsible for coordinating repositories/provider adapters.

Use explicit state machines

Represent order/payment/reservation states as finite states with guarded transitions, not loosely related booleans. Example: PAYMENT_PENDING → AUTHORIZED → CAPTURED or PAYMENT_PENDING → DECLINED; unknown timeout remains pending until provider query/callback resolves it.

For each transition define allowed source state, actor, durable write, emitted event, idempotency key, timeout/expiry, and compensation. Reject illegal transitions and record an audit reason. A late callback must not move a refunded order back to paid.

Command path and transaction boundary

  1. Authenticate caller and authorize access to cart/order.
  2. Validate request and idempotency key; compare canonical request hash.
  3. Load required state and enforce business invariants in the owning transaction.
  4. Persist state, idempotency outcome, and outbox event atomically where they share a database.
  5. Commit before calling non-transactional remote providers; continue saga using stable operation identity.
  6. Return a truthful confirmed, rejected, or pending result with a queryable resource.

Concurrency: optimistic versus pessimistic

Optimistic concurrency: update with expected version, such as UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?; zero rows means conflict and requires reread/retry or a clear conflict response. Useful when contention is modest.

Pessimistic locking: lock the row for a short transaction when conflicting operations are common and serialized decisions are required. Keep transactions short, acquire rows in consistent order, set lock timeouts, and monitor deadlocks. Neither replaces idempotency across client retries.

Repository and adapter boundaries

Keep business logic independent of provider-specific response formats. A payment adapter translates authorize/query/refund calls into a stable internal result such as approved, declined, or unknown. A repository owns persistence mechanics; an application service coordinates use cases.

Avoid abstractions that only rename a single database call. Introduce interfaces where they isolate a volatile external dependency, enable meaningful tests, or protect a domain boundary. Do not hide transaction boundaries behind methods with surprising behavior.

Thread safety and resource lifetime

Assume a web process handles requests concurrently. Do not keep mutable request/user/order state in shared singleton fields. Make shared caches and in-memory deduplication safe, but remember process-local coordination does not coordinate across instances.

Bound database pools, HTTP connection pools, worker concurrency, and buffers. Propagate deadlines/cancellation to remote calls. Release locks and resources on every path; avoid holding a database transaction while waiting on payment, email, or shipping networks.

Errors are part of the domain contract

Distinguish validation failure, forbidden access, conflict/out-of-stock, transient dependency failure, and unknown external outcome. Preserve causal identifiers for support without exposing secrets. Retry only classified transient failures within one total deadline and a retry budget.

Do not convert every exception to “success” or “not found.” Return actionable, stable errors and keep internal diagnostics in protected logs/traces. Reconciliation is a first-class path for ambiguous external outcomes.

Test invariants and race conditions

  • Property/invariant tests: available stock never goes negative; order total equals immutable line snapshots and pricing rules.
  • Concurrency tests: many simultaneous attempts for one remaining unit yield at most one reservation.
  • State-machine tests: illegal and late/out-of-order callbacks cannot regress terminal state.
  • Idempotency tests: same key/request returns same outcome; changed request with same key conflicts.
  • Contract tests: adapters handle timeout, duplicate callback, malformed response, and provider schema change.
  • Integration tests: transaction rollback leaves neither partial business state nor missing outbox record.

Protocols and platform: how requests travel through a system

A design is only as fast and reliable as the complete request path. Select protocols based on interaction shape, payload, clients, and failure semantics—not because one protocol is universally best.

Trace a browser request hop by hop

Client resolves a name through DNS, establishes a transport connection, negotiates TLS, sends an HTTP request, and receives a response through edge protection/CDN, load balancing, gateway, application, cache, database, or downstream service.

Each hop can add latency, queueing, retries, and a separate timeout. Carry a request/correlation ID, propagate a deadline, measure per-hop latency, and distinguish connection failure from an application error. Keep sensitive data out of URLs and logs.

HTTP, REST, GraphQL, and RPC

  • HTTP/REST-style APIs: broad client compatibility, cache-friendly reads, clear resource/action semantics; define pagination, error shapes, idempotency, and version compatibility.
  • GraphQL: client-selected fields and aggregation across data; enforce depth/cost limits, authorization per field, batching, and cache strategy to prevent expensive fan-out.
  • gRPC/RPC: typed service-to-service contracts and efficient streaming; manage code generation, deadlines, compatibility, browser support, and operational visibility.
  • WebSocket / server-sent events: live updates; manage connection scale, authorization, heartbeat, reconnect, fan-out, ordering, and fallback.

Use a synchronous protocol for a response the caller needs now; use durable messaging when work must survive caller disconnects or be independently retried.

DNS, TLS, connections, and latency

DNS maps names to endpoints and can influence regional routing, but caches mean changes are not instantly global. TLS protects transport and authenticates endpoints. Connection reuse avoids repeating handshakes; connection pools must be bounded and sized against downstream limits.

Budget an end-to-end deadline across all hops. If a client has 2 seconds total, do not allow three downstream calls each to wait 2 seconds. Propagate remaining deadline and cancellation; retries consume that same budget.

Edge, CDN, gateway, and load balancer

CDN serves cacheable public content near users; WAF/DDoS controls filter abusive traffic; load balancers distribute work and remove unready instances; API gateways apply shared edge policies such as routing, coarse auth, quotas, and request-size limits.

Business authorization and domain rules remain with the domain owner. Configure forwarded-client metadata carefully, preserve trace context, and avoid treating a health endpoint as proof that every dependency is healthy.

Database and data systems: choose storage from access and correctness

Start with the entities, invariants, query patterns, retention, and recovery requirements. A database is not just a place to put JSON: it determines concurrency, failure, cost, and how the product can evolve.

Relational data and transactions

Relational databases fit structured relationships, constraints, joins, and multi-row transactions. ACID means atomicity, consistency, isolation, durability; it does not mean every business workflow across independent services is one transaction.

Know transaction boundaries, isolation anomalies, uniqueness/foreign-key constraints, lock duration, deadlocks, and retryable serialization conflicts. Put critical invariants in durable database constraints or conditional writes—not only in application pre-checks.

Indexes and query plans

An index speeds selected reads at the cost of storage and write work. Composite index column order matters; a query may not benefit if filters/sorts do not match the index prefix. Use execution plans to inspect scans, row estimates, join strategy, sort spills, and actual versus estimated rows.

Watch N+1 queries, unbounded scans, large offsets, over-fetching, and indexes added without write/storage cost review. Cursor pagination over a stable indexed sort often behaves better for deep pages.

Isolation and concurrency anomalies

Read committed, repeatable read, and serializable provide different protections and costs; exact semantics vary by database. Common anomalies include dirty/non-repeatable reads, phantoms, lost updates, and write skew.

Choose the weakest isolation that preserves the business invariant, supported by constraints, atomic updates, optimistic version checks, or explicit locks. Retry serialization/deadlock failures only by rerunning the whole safe transaction with a bounded policy.

Data model families

  • Key-value: lookup by known key; session/state/low-latency access.
  • Document: aggregate-shaped records with flexible fields and known access paths.
  • Wide-column: high-scale partitioned access designed around row-key queries.
  • Graph: relationship traversal is central to the workload.
  • Time-series: timestamped measurements with retention/downsampling needs.
  • Search index: relevance, text analysis, facets, and derived document search.

For each, state partition key, hot-key risk, consistency promise, query limitations, backup/recovery, and how to migrate. Polyglot persistence is justified by distinct workload needs, not by using many databases for variety.

Replication, partitioning, and sharding

Replication copies data for availability/read capacity; it introduces lag and failover semantics. Partitioning divides data, often to manage table size or locality. Sharding distributes partitions across independent write capacity, adding routing, rebalancing, cross-shard query/transaction, and hot-partition complexity.

Choose a key that distributes expected load and supports required access patterns. Plan for skew, growth, resharding, global IDs, tenant isolation, and a hot customer/product. Rehearse failover with fencing to prevent two primaries accepting writes.

OLTP, OLAP, CDC, and analytics

OLTP serves small, concurrent business transactions. OLAP scans and aggregates large datasets. Do not run broad analytical scans against a checkout primary if they can starve user transactions.

Replicate changes through CDC/events into a warehouse/lake or read model. Track schema evolution, event time versus processing time, late data, deduplication, deletion propagation, data quality, lineage, access controls, and retention. Derived analytics can be rebuilt; financial ledger truth needs explicit immutable/audited semantics.

Schema evolution and data lifecycle

Use expand → deploy compatible readers/writers → backfill → verify → contract. Large backfills need rate limits, checkpoints, idempotence, progress metrics, and an abort plan. Dual-read/write periods require a clear single authority and reconciliation.

Define retention, archive, deletion, legal hold, export, backup expiry, and how caches/search/analytics copies follow privacy requirements. A delete from the primary does not automatically erase every replica, log, backup, or derived index.

Data correctness and migration safety

Use checksums/count comparisons, reconciliation reports, shadow reads, and domain invariants when migrating. Validate money totals, row counts, uniqueness, referential integrity, and event continuity. Make migrations restartable and observable; do not make a one-time migration script the only recovery mechanism.

Distributed-system primitives: coordination has a cost

A distributed system has independent clocks, failures, networks, and partial knowledge. No participant can infer global truth from a timeout. Use coordination only where a business invariant requires it.

Time, ordering, and identifiers

Wall clocks can drift and move; timestamps from different machines do not prove causal order. Use database sequence/version, partition offset, or explicit aggregate sequence when ordering matters. Store UTC instants and timezone/locale context where business calendar rules require them.

IDs should meet uniqueness, index locality, privacy, and generation availability needs. A UUID-like ID avoids central coordination but is not automatically sortable, secret, or authorization. Never use an opaque ID as a substitute for access control.

Leader election, leases, and fencing

A lease grants temporary ownership but a paused process may resume after its lease expires. A fencing token (monotonically increasing generation) lets the resource reject stale owners. Without fencing, two workers can both believe they are leader.

Use a mature coordination system for distributed leadership; do not build correctness on local clocks or a cache lock alone. Prefer idempotent work partitioning when it avoids a global leader.

Quorums and consensus in plain language

Replicated systems may require acknowledgements from a quorum to read/write or elect a leader. More coordination can improve agreement but costs latency and may reduce availability during partitions. Configuration and failure model matter; “three replicas” alone does not explain durability.

Consensus protocols help nodes agree on a log/leader under stated assumptions; they do not make application workflows atomic across unrelated databases and external payment providers.

CAP, PACELC, and consistency promises

During a network partition, a distributed data system must choose whether to reject some operations to preserve a consistency guarantee or accept operations that may diverge. Outside a partition, stronger coordination can still trade latency for consistency.

Define the user-visible promise per operation: read-your-writes, monotonic reads, bounded staleness, or linearizable behavior. “Eventually consistent” is incomplete unless you state expected lag, convergence/recovery, and what users may observe meanwhile.

Exactly-once: distinguish delivery from effect

A broker may offer deduplicated/transactional delivery within a defined boundary, but a database write plus external payment/email is not automatically exactly once. Common practical design is at-least-once delivery plus an idempotent business operation and durable deduplication key.

Retain dedupe records for the full replay/retry horizon. Make external effects queryable or reconcilable; a local “processed” flag cannot prove a remote provider did nothing after a timeout.

Retries, deadlines, and retry budgets

Retry only errors classified as transient, for operations that are idempotent or protected by an idempotency key. Use exponential backoff with jitter, maximum attempts, an overall deadline, and a retry budget per dependency.

Multiple retrying layers multiply load. Do not retry validation/authorization errors; honor server retry guidance; use circuit breakers and admission control to stop amplifying an outage.

Distributed locks: last resort for invariants

A distributed lock can expire, be delayed, or be held by a paused worker; lock correctness needs ownership token/fencing and careful release. For inventory, booking, or uniqueness, prefer a database constraint or atomic conditional update at the authoritative owner when possible.

If a lock is necessary, define lease, fencing, renewal, crash behavior, fairness, partition behavior, and metrics. Never rely on “we have a lock” without proving stale holders cannot commit.

Backpressure and overload behavior

Bound queues, concurrency, memory, payload size, and waiting time. Apply admission control before saturating the dependency. Shed optional work first, preserve enough capacity for recovery/control paths, and return a clear retryable response when refusing work.

Domain-driven design at practical depth

Identify bounded contexts with distinct language and rules: Catalog, Ordering, Inventory, Payments, Fulfillment, Seller Settlement. A context owns its model and decisions; an anti-corruption layer translates an external/provider model rather than spreading vendor terms through the domain.

Context boundaries are hypotheses. Validate them through change patterns, invariants, team ownership, and integration friction; do not treat every noun as a service.

Choosing orchestration versus choreography

Orchestration: a process manager explicitly tracks workflow state, timeouts, and next actions; easier to understand long checkout processes but centralizes coordination.

Common application blueprints: reuse reasoning, not diagrams

Different products share building blocks but have different hard invariants. Use these mini-cases to practice transferring the method beyond MarketSquare.

Chat and real-time collaboration

Core needs: durable messages, conversation membership/authorization, per-conversation ordering, online presence, reconnect and history sync. Use persistent storage as truth; WebSockets deliver live updates but are not the durable message record. Design fan-out for large groups, offline delivery, dedupe, retention, and encryption requirements.

Ask whether messages are end-to-end encrypted, searchable, editable, or ephemeral; each changes key management, indexing, compliance, and recovery.

News feed and social timeline

Core choice: fan-out-on-write, fan-out-on-read, or hybrid. Write fan-out makes reads fast but celebrity/follower bursts expensive; read fan-out avoids huge writes but can make reads slow. Use ranking as a derived, rebuildable view and paginate with stable cursors.

Track freshness, duplicate posts, deleted/blocked content, privacy changes, and backfill/recompute behavior.

URL shortener

Core needs: unique short-code creation, fast redirect, abuse controls, expiration/custom aliases, analytics. Put redirect reads on a highly cacheable path; preserve collision/uniqueness at the write owner; keep analytics asynchronous so they do not delay redirects.

Decide whether links are guessable, revocable, tenant-scoped, and permanent; protect against malicious destination and redirect abuse.

File upload and media processing

Upload directly to object storage with a short-lived scoped token; confirm metadata and ownership through the API. Validate size/type, scan/quarantine, process asynchronously, generate renditions, and publish only after safety checks. Use checksums and idempotent job IDs.

Plan resumable multipart upload, abandoned-upload cleanup, CDN cache invalidation/versioning, lifecycle/retention, and cost for egress and transformations.

Ride dispatch / appointment booking

Hard problem: allocate a scarce, changing resource without double assignment under concurrent requests. Model a durable reservation/assignment state machine, use geographic or time-window candidate lookup, then validate/claim with an atomic owner-side operation.

Use expiration and cancellation semantics, idempotent client intents, fairness/priority rules, and explicit behavior when location or availability data is stale.

Notification platform

Separate business intent from channel delivery. Store recipient, template/version, preference/consent, and idempotency identity; queue by priority; rate-limit per provider/tenant; retry transient failures and dead-letter permanent failures. Delivery is not proof the user saw the message.

Respect opt-outs, quiet hours, localization, provider callbacks, deduplication, and privacy in templates/logs.

Video / streaming delivery

Separate ingest, validation/transcoding, metadata/catalog, entitlement, and playback delivery. Store media in object storage and distribute through CDN; process encoding asynchronously and track job state. Protect origin from cache misses and plan bandwidth/egress.

Playback manifests, adaptive bitrate, DRM/licensing, regional content rules, and live versus on-demand delivery create specialized requirements beyond a generic CRUD design.

Analytics and event pipeline

Capture events with schema/version, event ID, event time, actor/tenant, and privacy classification. Validate, deduplicate, partition, retain, and process late/out-of-order events. Separate operational transactions from analytical scans.

Define delivery objective, replay window, correction/backfill behavior, data quality checks, lineage, retention, and access controls before choosing batch or streaming infrastructure.

Beyond marketplaces: recognize the hard problem, then write the core code

System design transfers across products, but the critical invariant changes. A booking app protects a scarce time slot; chat protects message order and membership; a ledger protects balanced financial records; an IoT platform handles high-volume time-stamped signals. Start with that invariant, not with a copied marketplace diagram.

Appointment / room / seat booking

Hard problem: two requests racing for one slot. Use a relational source of truth and an atomic claim or unique constraint. Add expiring holds only when the UX requires a payment window; define expiration versus late payment.

First architecture: ASP.NET Core API + SQL database; notifications are asynchronous. Add calendar integration only after defining ownership and conflict semantics.

Chat / collaboration

Hard problem: durable per-conversation ordering, membership/authorization, fan-out, reconnect, offline history. Persist messages first; WebSocket/SSE is delivery, not truth. Use a partition/order key such as conversation ID and cursor-based history.

Microsoft-oriented options: Azure SignalR Service can manage connection fan-out; a durable event pipeline and database remain responsible for message persistence and replay.

Banking / wallet / accounting ledger

Hard problem: money must be auditable and balanced; retries must not create another transfer. Model immutable ledger entries, currency, idempotency, authorization, reconciliation, and explicit holds/settlement. Never treat a cached balance as authoritative.

First architecture: strongly consistent transactional database, append-only ledger semantics, strict access/audit controls, and reconciliation jobs. A distributed cache or eventual write path must not decide whether a transfer is valid.

IoT telemetry / device platform

Hard problem: huge ingest rate, device identity, intermittent connectivity, duplicate/out-of-order readings, and time-window queries. Authenticate devices, buffer safely, partition by device/time, retain raw data according to policy, and build downsampled aggregates.

Azure-oriented options: evaluate IoT Hub for device connectivity/management, Event Hubs for high-throughput event ingestion, and Azure Data Explorer or an analytics store for time-series exploration. Select only after confirming protocol, region, retention, throughput, and cost fit.

Social feed / news timeline

Hard problem: distribution skew and personalization. Fan-out-on-write gives fast reads but makes celebrity posts expensive; fan-out-on-read saves writes but increases feed latency. Use a hybrid for extreme accounts, cursor pagination, and rebuildable ranking projections.

Enforce block/privacy changes at read time or through a reliable invalidation model; never let a stale feed projection override current authorization.

Document / photo / video processing

Hard problem: large upload bandwidth, untrusted files, asynchronous processing, and delivery cost. Upload directly to scoped object storage, quarantine and scan, process through durable jobs, publish derived versions, and serve via CDN.

Microsoft-oriented options: Azure Blob Storage for objects, Functions or Container Apps jobs for event-driven processing, and Azure Front Door/CDN for delivery where regional and product requirements fit.

Multi-tenant SaaS

Hard problem: tenant isolation, noisy neighbors, per-tenant authorization/configuration, and data residency. Put tenant identity in trusted claims; enforce it in every query/write; add quotas and tenant-aware telemetry.

Choose shared tables with tenant keys for simpler operations, separate databases for stronger isolation/compliance, or a hybrid by tier. Plan tenant migration, backup/restore, key management, and cross-tenant access testing.

Video meeting / live presence

Hard problem: real-time media latency and network variability, not ordinary CRUD throughput. Separate signaling/control plane from audio/video media plane; use WebRTC or managed real-time media infrastructure, TURN for restrictive networks, and explicit regional routing.

Measure join time, packet loss, jitter, and media quality. A typical HTTP microservice architecture does not itself transport real-time media efficiently.

    }

    if (string.IsNullOrWhiteSpace(request.IdempotencyKey)
        || request.IdempotencyKey.Length > 100)
    {
        return Results.BadRequest(new { error = "Invalid idempotency key." });
    }

    var previous = await db.Bookings.AsNoTracking()
        .SingleOrDefaultAsync(
            b => b.CustomerId == customerId
                 && b.IdempotencyKey == request.IdempotencyKey,
            ct);

    if (previous is not null)
    {
        return previous.SlotId == request.SlotId
            ? Results.Ok(new { previous.Id, previous.SlotId, previous.Status })
            : Results.Conflict(new { error = "Key was used for another request." });
    }

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var claimed = await db.Slots
        .Where(s => s.Id == request.SlotId
                    && s.State == SlotState.Available)
        .ExecuteUpdateAsync(update => update
            .SetProperty(s => s.State, SlotState.Booked)
            .SetProperty(s => s.BookedByCustomerId, customerId), ct);

    if (claimed == 0)
    {
        return Results.Conflict(new { error = "Slot is no longer available." });
    }

    var booking = new Booking
    {
        Id = Guid.NewGuid(),
        CustomerId = customerId,
        SlotId = request.SlotId,
        IdempotencyKey = request.IdempotencyKey,
        Status = "Confirmed",
        CreatedAtUtc = DateTimeOffset.UtcNow
    };

    db.Bookings.Add(booking);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);

    return Results.Created($"/bookings/{booking.Id}",
        new { booking.Id, booking.SlotId, booking.Status });
}).RequireAuthorization();

app.Run();

Why the database decides: both requests may observe “available” in memory, but the conditional UPDATE ... WHERE State = Available is atomic at the database. One update affects one row; the competing update affects zero. An in-process lock would not coordinate different app instances.

Production hardening: configure the actual JWT issuer/audience and policies; validate the slot’s provider/time window; use typed status values; store a canonical request hash with the idempotency key; handle a concurrent duplicate-key insert by re-reading and returning the original result; map provider-specific unique violations explicitly; add cancellation/reschedule rules, audit events, rate limits, tests, and an outbox if notifications must reliably follow confirmation. Never expose the connection string in source; use managed identity/Key Vault as appropriate.

One complete system-design checklist for any new product

Use this sequence in a real project or interview. The output is a defendable design with assumptions, boundaries, and a safe path to change—not merely a component diagram.

  1. Product and scope: identify actors, primary journeys, business outcome, launch slice, out-of-scope work, external systems, and assumptions that need validation.
  2. Requirements: write functional requirements and measurable latency, availability, correctness, freshness, privacy, durability, recovery, and cost targets by user journey.
  3. Workload: estimate users, request mix, average/peak/burst, concurrency, payload, storage growth, retention, fan-out, hot keys, and dependency quotas. Label uncertain estimates.
  4. Domain and invariants: identify entities, lifecycle/state machines, business invariants, source of truth, authorization boundary, and audit needs.
  5. Contracts: define API/events, authentication/authorization, idempotency, pagination, versioning, errors, timeouts, retry semantics, and rate limits.
  6. Data: choose model and transaction boundary from access and consistency needs; define indexes, partition keys, backup, replication, migration, retention, and deletion.
  7. Baseline HLD: draw client, edge, app/modules, stores, cache, search, queue, external dependencies, and deployment/failure domains. Trace one read and one critical write.
  8. Critical LLD: define responsibilities, state transitions, transaction boundary, concurrency control, error types, resource limits, and tests for races/invariants.
  9. Failure design: walk through timeouts, retry/duplicate, partial commit, dependency outage, cache miss/stampede, queue backlog, zone loss, bad deploy, and data corruption.
  10. Security and privacy: threat-model assets and trust boundaries; cover identity, object authorization, secrets, encryption, abuse, audit, retention, and incident response.
  11. Operations: define SLI/SLO, dashboards, alerts, traces, runbooks, deploy/rollback, capacity tests, restore drills, on-call ownership, and cost controls.
  12. Trade-offs and evolution: compare simpler options, explain chosen costs, state the trigger to revisit, and plan compatible migrations rather than a big-bang rewrite.

Deliverables to leave behind

  • Context diagram and critical request/data-flow diagrams.
  • Requirements, SLOs, assumptions, traffic estimates, and decision log.
  • API/event contracts, data ownership map, schemas, and state machines.
  • Threat model, failure-mode table, operational dashboard/runbook outline.
  • Migration/rollout plan, test plan, cost estimate, unresolved risks and owners.

Questions a senior designer should answer

  • What is the bottleneck and what evidence proves it?
  • Which invariant must survive concurrency and failover?
  • What happens if the caller times out after the side effect commits?
  • How do we know the service is healthy from the customer's view?
  • How can we roll out, roll back, restore, or migrate without data loss?
  • Which operational burden are we choosing, and who owns it?
  • What evidence would make this design wrong or require evolution?

14. Quick glossary

Availability: proportion of time a service meets its defined success criteria.
Latency p95: 95% of measured requests complete at or below this duration.
Idempotency: repeating an operation with the same identity does not repeat its business effect.
Consistency: rules governing when reads observe successful writes.
Eventual consistency: replicas/projections converge if updates stop and processing recovers.
Outbox: durable event record written in the same transaction as a business update.
Saga: distributed workflow of local transactions with retries and compensating actions.
Backpressure: slowing or rejecting incoming work when downstream capacity is constrained.
Bulkhead: resource isolation that prevents one workload/dependency from exhausting everything.
SLO / SLI: target for a measured service objective / the underlying indicator.
RTO / RPO: target recovery time / maximum acceptable data loss window.
Hot key: one partition/cache key receiving a disproportionate share of requests.

This guide is a learning framework, not a universal architecture prescription. Choose technologies and targets only after validating product requirements, workload, team capability, cost, and regional/compliance constraints.
