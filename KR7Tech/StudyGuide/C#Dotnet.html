One-line: Encapsulation protects state and exposes controlled behavior.
Interview answer: I keep fields private and expose operations through methods or properties so callers cannot create an invalid state.

3. What is abstraction?

🎛️ Steering wheel hides mechanics
Caller → Contract → Hidden Implementation

4. What is inheritance?

🌳 Child inherits family features

Interview answer: It models an is-a relationship, although I prefer composition when behaviors must vary independently.

5. What is polymorphism?

🔌 Same socket, different devices
Interface → Implementation A / B / C
One-line: One contract can execute different implementations.
Interview answer: Runtime polymorphism is commonly achieved through interfaces or virtual method overriding.

6. Interface vs abstract class?

📜 Contract vs 🏠 parent house
Interface = capability | Abstract = shared base
One-line: An interface defines a contract; an abstract class can share state and implementation.
Interview answer: I use interfaces for loose coupling and capabilities, and abstract classes for closely related types with common behavior.

7. Overloading vs overriding?

🚪 Multiple entrances vs rebuilt room

Interview answer: Overloading is compile-time polymorphism, while overriding is runtime polymorphism.

8. Value type vs reference type?

📦 Value vs 🏷️ address card

One-line: Value types contain data directly; reference types point to objects.
Interview answer: Assignment copies a value for value types, while reference-type assignment normally copies the reference.

9. Single Responsibility Principle?

👷 One employee, one job

🔌 Add plug-in, do not rewire

One-line: Software should be open for extension and closed for unnecessary modification.
Interview answer: I extend behavior through strategies, interfaces, or composition rather than repeatedly changing stable code.

11. Liskov Substitution Principle?

12. Interface Segregation Principle?

🍽️ Small menu

13. Dependency Inversion Principle?

🎮 Remote depends on protocol

Interview answer: Business logic and infrastructure communicate through contracts, improving testability and substitution.

14. Factory, Strategy, and Decorator?

🏭 Create, 🗺️ choose, 🎁 wrap

🔬 What .NET Actually Does — Follow One Order Request

The interview bank above gives fast answers. This section opens the machinery underneath them. Follow a customer submitting an order: from C# source, through the running process, to the database response. Exact optimizations vary by runtime version, operating system, hosting model, and database provider; the execution model below is the useful mental model for debugging and design.

🧾 C# source🛠️ Roslyn → IL + metadata ⚙️ CLR loads + JIT🌐 Kestrel + middleware 🧩 Endpoint + DI⏳ Async I/O 🗄️ EF Core + database🧹 GC + response

1. From C# text to CPU instructions

📝 Source is a recipe; IL is portable packaged work
.cs → Roslyn parse/bind/type-check → IL + metadata → assembly → CLR load → JIT native code

Build time: the C# compiler parses files into syntax trees, resolves names and overloads, checks types and language rules, and emits Common Intermediate Language (CIL/IL) plus metadata into an assembly. Metadata describes types, methods, references, and attributes; it is why reflection and many serializers can inspect code at runtime.

Run time: the host starts the .NET runtime, which resolves dependencies and loads types as needed. A method may be compiled to machine code by the JIT when first needed; tiered compilation can later recompile hot methods with stronger optimizations. ReadyToRun can provide ahead-of-time native code for some methods, while the runtime may still JIT other code. So “C# is compiled” and “the JIT compiles methods” describe different stages.

What to remember: C# is not interpreted line by line. Build output contains IL and metadata; the runtime turns executable methods into native instructions and supplies services such as type loading, exceptions, garbage collection, and interop.
dotnet build -c Release dotnet --info // For investigation: inspect assembly metadata/IL, then profile the running process. // JIT, tiered compilation, and ReadyToRun details depend on deployment/runtime settings.

2. What happens when HTTP reaches ASP.NET Core?

🛂 A request passes through an ordered chain of gates
Socket bytes → Kestrel parses HTTP → HttpContext → middleware delegates → route/endpoint → response bytes

Kestrel accepts network traffic and parses the HTTP protocol into request data represented by HttpContext. During startup, each Use... call wraps the next request delegate. At runtime, the request enters the first middleware; each component can inspect or change the context, call the next delegate, or finish early (for example, reject an unauthenticated request).

Routing selects an endpoint. Authentication establishes the principal; authorization checks policy. Endpoint binding reads route, query, header, or body data and validates it. The endpoint invokes application code. The result is formatted (often JSON) and written back through the response path. Middleware order matters: exception handling and routing need to be placed so they can observe the work they are responsible for.

app.UseExceptionHandler("/error"); app.UseRouting(); app.UseAuthentication(); app.UseAuthorization(); app.MapPost("/orders", CreateOrder);
Debug it: Put a trace/log scope at request entry and exit; record the selected route, status code, elapsed time, and trace ID. Do not log authorization headers, secrets, or full sensitive request bodies.

3. How does dependency injection create an endpoint's services?

🧰 The container follows a constructor graph and owns scoped cleanup
Endpoint asks for service → constructor dependencies resolved → scope cache checked → instance supplied → scope disposed

At startup, registrations describe service-to-implementation mappings and lifetimes. When an endpoint needs IOrderService, the built-in container follows its constructor dependencies and creates the required object graph. Singleton instances are shared by the root provider; scoped instances are reused inside one scope (for web requests, normally one request scope); transient instances are created for each resolution. These are lifetime rules, not thread-safety guarantees.

The request scope also tracks disposable services it creates and disposes them when that scope ends. A singleton must not capture a request-scoped service such as a DbContext; doing so leaks the wrong lifetime across requests. Creating a scope for background work is explicit—the request scope does not follow a queued job after the response ends.

builder.Services.AddDbContext<OrdersDbContext>(options => options.UseSqlServer(connectionString)); // scoped by default builder.Services.AddScoped<IOrderService, OrderService>(); builder.Services.AddSingleton<IOrderRules, OrderRules>();
Check the design: Is the service safe to share? Does its dependency have a longer or shorter lifetime? Who disposes it? DI can construct objects, but it cannot make mutable singleton state thread-safe.

4. What does await do while a database call is waiting?

⏸️ The method saves its place; it does not park a worker for I/O
Call async API → operation pending → save state + return Task → I/O completes → continuation resumes

The compiler transforms an async method into a resumable state machine. Execution runs normally until an await. If its awaiter is already complete, execution can continue immediately. If it is incomplete, the state machine records what it needs to continue, registers a continuation, and returns control to its caller. The caller can process other work instead of blocking that thread.

For socket/database I/O, the API asks the operating system or provider to perform the operation asynchronously. While it waits, the request does not need to occupy a worker thread just to sleep. Completion later schedules the continuation. This is not a promise that every continuation uses a new thread: it may run inline or on an appropriate scheduler. ASP.NET Core normally does not install a request-specific SynchronizationContext. CPU-heavy work is different; it still consumes CPU and needs capacity planning.

var order = await db.Orders .SingleOrDefaultAsync(x => x.Id == id, cancellationToken); // While the query is pending, this method can return control to the server. // The request's logical work resumes after completion or cancellation.
Important distinction: Task represents an operation's eventual result; Thread is an execution resource. Task.Run can queue CPU work to the pool; it does not make database or HTTP I/O more asynchronous.

5. Why does an EF Core LINQ query not run immediately?

🧾 IQueryable describes a query; the provider decides how to execute it
LINQ operators build expression tree → terminal operator → provider translates query → database executes SQL

With LINQ to Objects, operators usually run delegates over objects in memory. With EF Core, DbSet<T> exposes IQueryable<T>; operators such as Where and Select build an expression tree describing the query. EF Core's provider translates the translatable part into parameterized SQL when a terminal operation (for example, ToListAsync, SingleAsync, or enumeration) requests results.

This distinction explains why a C# method call inside a query may not translate to SQL, why query composition can remain cheap, and why enumerating the same query twice can execute it twice. Materializing a full entity can enable change tracking; projecting only the needed columns into a DTO can reduce transferred data and avoid tracking when the result is read-only.

var summaries = await db.Orders .Where(order => order.CustomerId == customerId) .OrderByDescending(order => order.CreatedAt) .Select(order => new OrderSummary(order.Id, order.Status, order.Total)) .Take(20) .ToListAsync(cancellationToken); // execution/materialization happens here
Watch out: Do not assume every C# expression can be translated. Inspect generated SQL and query plans for slow database work; moving a filter to AsEnumerable() changes later operators to in-memory work and may pull too many rows across the network.

6. What happens between EF Core and the database?

📨 A query becomes parameterized commands and rows become objects
EF query → provider SQL + parameters → connection/driver → database plan + execution → rows → materialized results

EF Core asks the provider to translate the expression tree, then uses the database driver to send commands and parameters. The database parses or reuses a plan, checks indexes and data, and returns rows over the connection. EF materializes objects from those rows. For tracking queries, the change tracker maintains identity and original values so the same database identity can be represented consistently within the context. For read-only work, AsNoTracking can avoid that bookkeeping.

On SaveChangesAsync, EF detects changes (unless configured otherwise), creates the required insert/update/delete commands, and asks the provider to execute them. Relational providers normally use a transaction for a single SaveChanges operation when supported, but multi-step business workflows and multiple services need their own explicit consistency design. A DbContext is a short-lived unit-of-work and is not thread-safe: do not run parallel queries on the same instance.

var order = new Order(customerId, lines); db.Orders.Add(order); await db.SaveChangesAsync(cancellationToken); // One context owns this unit of work. Await each operation before reusing it.
Diagnose the whole path: application query shape, generated SQL, round-trip count, connection-pool wait, database execution plan, returned row count, and materialization/tracking cost. “EF is slow” is not yet a root cause.

7. How do managed objects get allocated and collected?

🧹 GC reclaims unreachable memory, not objects when a method returns
Allocate → roots reference object graph → mark reachable → reclaim/compact eligible regions → update references

Many small managed objects are allocated quickly from a thread-local allocation region. When allocation pressure crosses a threshold, the garbage collector identifies roots such as references in active stacks, static fields, and runtime handles, then traces which objects remain reachable. Unreachable objects can be reclaimed. Some regions are compacted, moving objects and updating managed references; pinning and special allocation regions constrain movement. Collection strategy and pause behavior depend on runtime mode and workload.

Generations are an optimization based on the observation that many objects die young: short-lived objects are collected more often, while survivors may be promoted. A managed “memory leak” usually means an object is still reachable—for example, through a static collection, an event subscription, a cache without an eviction policy, or a pending task. GC manages memory, not deterministic release of files, sockets, and other external resources; use using/await using for those.

Measure before tuning: compare allocation rate, heap size, collection counts and pauses, and retained-object paths. Use dotnet-counters for live runtime counters and a trace or dump when the counters show a problem; avoid using GC.Collect() as routine cleanup.

8. What happens when your service calls another API?

🌍 Reuse a connection pipeline; do not create a socket per request
HttpClient → handler pipeline → pooled connection → DNS/network → remote service → response body

HttpClient sends through an underlying handler, which manages connections and protocol behavior. Repeatedly creating and disposing handlers can waste connections and cause port exhaustion; using one client forever can make connection/DNS refresh behavior difficult to manage. In ASP.NET Core, IHttpClientFactory creates configured clients while pooling and rotating handlers according to its lifetime configuration. A typed client can keep a dependency's base address, policies, and serialization together.

An async send waits without dedicating a thread to the network wait, but the operation still consumes a connection, memory, a request budget, and remote capacity. Propagate cancellation, configure timeouts, bound concurrency, and use retries only when safe for the operation. Retrying a non-idempotent order submission without an idempotency design can create duplicate orders.

builder.Services.AddHttpClient<InventoryClient>(client => { client.BaseAddress = new Uri(inventoryBaseUrl); client.Timeout = TimeSpan.FromSeconds(5); }); var stock = await inventory.GetStockAsync(sku, cancellationToken);
Production question: What is the timeout budget? What happens if the caller cancels? Is this operation safe to retry? How will you distinguish connection-pool wait, network latency, and a slow remote server?

9. Put the pieces together: POST /orders

🧭 Trace the same request across every layer
Client → auth → endpoint → order service → EF/SQL → commit → JSON response
app.MapPost("/orders", async ( CreateOrderRequest request, IOrderService orders, CancellationToken cancellationToken) => { var order = await orders.CreateAsync(request, cancellationToken); return Results.Created($"/orders/{order.Id}", new { order.Id, order.Status }); }).RequireAuthorization();

Walk the request: (1) Kestrel parses the HTTP request and creates its context. (2) Middleware handles errors, routing, authentication, and authorization in configured order. (3) The selected endpoint binds and validates the input; DI supplies the request-scoped service graph. (4) The service applies business rules and composes an EF query or entity changes. (5) EF and its provider send parameterized SQL; the database executes it. (6) Async continuations resume as results arrive, and SaveChangesAsync completes the unit of work. (7) The endpoint creates a result; ASP.NET Core serializes it and Kestrel writes the response. Short-lived objects become collectible when no longer reachable; the request scope disposes owned services.

Practice the failure path: What if validation fails, the user is unauthorized, the database times out, the client disconnects, or a retry arrives after the first commit? Decide which layer owns the response, cancellation, rollback, idempotency, and telemetry rather than treating the request as one method call.

10. What is the runtime difference between value and reference types?

📦 A value copies its data; a reference copies a location to an object
struct copy → independent value | class copy → shared object reference

A variable of a value type contains its value (or is stored as part of another value); assigning it copies that value. A reference-type variable contains a reference to an object. Assigning the reference copies the reference, so both variables can point to the same object. This distinction is about language semantics—not a promise that every struct is physically on the stack or every class lives in one fixed heap location.

Boxing converts a value to object or an implemented interface and typically creates a heap object containing a copy of the value. Unboxing checks the runtime type and extracts a value. Generic collections such as List<int> avoid the boxing required by older non-generic collections for many common operations. Large mutable structs can be expensive because copies propagate through parameters and returns; readonly structs and in parameters can help in measured cases.

int first = 5; int second = first; second++; // first is still 5 var original = new List<int> { 5 }; var alias = original; alias.Add(6); // original now observes 5, 6 object boxed = first; // value converted to object int unboxed = (int)boxed; // checked extraction
Use this when deciding: mutability, equality, copying, allocation, and API semantics. Choose a struct for a small value with value-like semantics—not merely to “put it on the stack.”

11. How do delegates, events, closures, and LINQ connect?

📣 A delegate is a callable reference; a closure also carries captured state
Method group/lambda → delegate → invocation | captured local → closure state

A delegate is a type-safe object that refers to one or more callable methods. A lambda can become a delegate for in-process execution. If it captures a local variable, the compiler preserves that captured state beyond the original stack frame, commonly by generating a closure object. That object remains reachable as long as the delegate remains reachable.

An event restricts who can raise a delegate notification, but subscribers still need lifecycle management: a long-lived publisher can retain a short-lived subscriber through its event handler. LINQ to Objects generally stores delegates and executes them while enumerating. LINQ over IQueryable builds expression data for a provider to translate. Deferred enumeration means side effects may run later or more than once, so materialize deliberately when a stable snapshot is required.

int minimum = 10; Func<int, bool> isLarge = value => value >= minimum; // captures minimum var query = values.Where(isLarge); // deferred for LINQ to Objects var snapshot = query.ToArray(); // enumeration executes here publisher.Changed += OnChanged; // Unsubscribe when the subscriber's lifetime ends.
Trace retention: If a supposedly temporary object never collects, inspect event subscriptions, closures stored in callbacks, timers, and deferred queries retained by long-lived services.

12. How do ASP.NET Core validation and security decisions happen?

🪪 Authentication identifies a principal; authorization checks its permission
Untrusted bytes → binding/validation → authenticate → authorize → business rule → data access

HTTP input is untrusted even when it binds to a strongly typed C# request. Binding converts route, query, header, and body values into application types; validation checks shape and constraints. Authentication validates credentials and creates a ClaimsPrincipal. Authorization evaluates policies against that principal and the requested resource. Neither step replaces business authorization—for example, checking that the current user owns the specific order being changed.

ASP.NET Core authentication handlers validate tokens or credentials according to their scheme. A JWT validation setup must validate signature and trusted issuer/audience and enforce lifetime; decoding a JWT is not validating it. Authorization should be deny-by-default for protected operations, use least-privilege policies, and check resource ownership at the service/data boundary. Return safe error details, avoid leaking secrets, and treat client-supplied IDs and role names as claims to verify—not proof of permission.

builder.Services.AddAuthorization(options => { options.AddPolicy("CanReadOrders", policy => policy.RequireAuthenticatedUser() .RequireClaim("permission", "orders.read")); }); app.MapGet("/orders/{id}", GetOrder) .RequireAuthorization("CanReadOrders"); // GetOrder must still verify that this principal may access this order ID.
Review the boundary: Are credentials validated by trusted middleware? Is the endpoint protected? Is access checked for this particular resource? Are secrets and personal data absent from logs and error responses?

13. How do EF Core transactions and optimistic concurrency protect updates?

🧾 Commit a unit together; detect if someone changed the row first
Read version V1 → another writer commits V2 → conditional update affects 0 rows → concurrency conflict

A database transaction groups operations so the database commits them atomically or rolls them back, subject to the provider and isolation level. One relational SaveChanges is normally transactional when the provider supports transactions. An explicit transaction is needed when several saves or queries must share one database boundary. A transaction cannot atomically include an unrelated HTTP call or message broker without a broader distributed consistency pattern.

Optimistic concurrency assumes collisions are uncommon. EF Core can include a configured concurrency token (for example a SQL Server rowversion) in the update predicate. If the stored token changed since it was read, the update affects no row and EF throws DbUpdateConcurrencyException. The application must decide whether to reload and retry, merge user changes, or return a conflict such as HTTP 409. Blindly retrying the same stale values can overwrite newer intent.

try { order.ChangeAddress(request.Address); await db.SaveChangesAsync(cancellationToken); } catch (DbUpdateConcurrencyException) { // Reload current state; merge or report a conflict intentionally. return Results.Conflict("Order changed; refresh and try again."); }
Be precise: transaction atomicity, isolation, optimistic concurrency, and idempotency solve different problems. A transaction does not stop stale user edits unless the update checks a concurrency token or equivalent condition.

14. Why can a database save succeed while message publishing fails?

📦 Two independent systems do not share one automatic commit
Save order ✓ → process stops → publish event ✗ → downstream never learns of order

A database transaction controls changes inside that database. Publishing to a broker is a separate network operation with its own failures and acknowledgements. If the app commits an order then crashes before publishing OrderCreated, the order exists but consumers are unaware. Reversing the sequence risks publishing an event for a transaction that later rolls back.

The transactional outbox writes the business change and an event record into the same database transaction. A background publisher reads unsent outbox rows, sends them, and marks them delivered. A crash can cause duplicate delivery, so consumers should be idempotent—often by recording a message ID in the same transaction as their effect. “Exactly once” across independent services is generally achieved as effectively-once business behavior through durable state, deduplication, and idempotency, not by assuming a network never retries.

Transaction: order + outbox row → commit → publisher retries → consumer deduplicates message ID
Choose it when: a committed business action must reliably trigger downstream work. Add monitoring for oldest pending outbox age, retry exhaustion, poison messages, and consumer lag.

15. How do Channels and backpressure prevent overload?

🚦 A bounded queue makes overload visible instead of hiding it in memory
Producers → bounded Channel<T> → limited consumers → downstream dependency

An unbounded in-memory queue accepts work faster than a slow consumer can process it, so backlog and memory use can grow without limit. A bounded Channel<T> gives the system a capacity limit. With BoundedChannelFullMode.Wait, writers asynchronously wait for room; other full modes can drop work and therefore require an explicit loss policy. Consumer count limits parallel work. Cancellation and channel completion make shutdown and failure states explicit.

A channel is in-process coordination, not durable storage: process termination loses queued items. Use a broker or durable database queue when work must survive restarts. A bounded queue also does not by itself protect a dependency if each consumer starts more parallel work downstream; propagate a concurrency budget to the actual constrained resource.

var channel = Channel.CreateBounded<WorkItem>( new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.Wait, SingleReader = false, SingleWriter = false }); await channel.Writer.WriteAsync(item, cancellationToken); await foreach (var work in channel.Reader.ReadAllAsync(cancellationToken)) await ProcessAsync(work, cancellationToken);
Look for starvation: thread-pool queue growth, blocked workers, sync-over-async, lock contention, and rising request latency. Raising thread minimums may hide symptoms; remove blocking or bound work at the source.

16. How do you test an ASP.NET Core application at the right boundary?

🧪 Test business rules cheaply, then prove framework and database wiring realistically
Unit → service behavior | Integration → host + HTTP + persistence | E2E → critical user journey

A unit test calls a small unit directly and controls its collaborators; it is fast and useful for domain rules. Too many tests that mock every repository can pass while routing, serialization, dependency injection, authentication, or EF mappings are broken. An integration test boots the real ASP.NET Core pipeline in a test host, sends HTTP requests, and exercises selected real boundaries. A production-like database provider is important for behaviors such as SQL translation, constraints, transactions, and concurrency; an in-memory substitute may not behave like the production database.

Keep tests deterministic: isolate data per test, avoid shared mutable fixtures, control time and external services, await async operations, and clean up owned resources. Use contract tests for compatibility between independently deployed services and a small number of end-to-end tests for the most valuable journeys.

[Fact] public async Task CreateOrder_returns_created_and_persists_order() { await using var factory = new WebApplicationFactory<Program>(); using var client = factory.CreateClient(); var response = await client.PostAsJsonAsync("/orders", request); Assert.Equal(HttpStatusCode.Created, response.StatusCode); // Query the test database to verify the persisted invariant. }
Test failure behavior too: invalid input, unauthenticated access, forbidden resource, database conflict, cancellation, duplicate request, and dependency timeout. Tests are executable claims about contracts, not only line coverage.

17. What does modular architecture change inside a .NET solution?

🧱 Dependency direction decides whether business rules survive infrastructure changes
HTTP/API → application use case → domain rules ← infrastructure implements required ports

A modular monolith can run as one deployable application while keeping business capabilities behind explicit module boundaries. The API translates HTTP into a command or query. The application layer coordinates a use case and its transaction boundary. The domain owns invariants and domain behavior. Infrastructure implements persistence, messaging, and external-service interfaces. Dependency inversion means the core declares the abstractions it needs; infrastructure references and implements those abstractions rather than making domain rules depend on an EF or cloud SDK type.

The value is not the number of projects or folders. It is the ability to change one capability without reaching into unrelated internals, and to test business rules without starting every external system. A repository abstraction is useful when it protects a meaningful domain or persistence boundary; wrapping every EF method in a generic repository can hide useful query and transaction behavior without creating real independence.

public interface IOrderStore { Task AddAsync(Order order, CancellationToken cancellationToken); } public sealed class PlaceOrder(IOrderStore store) { public async Task<OrderId> ExecuteAsync( PlaceOrderCommand command, CancellationToken cancellationToken) { var order = Order.Place(command.CustomerId, command.Lines); await store.AddAsync(order, cancellationToken); return order.Id; } }
Boundary test: Can a feature be tested without SQL, can infrastructure be replaced without editing domain rules, and does each module own its data and vocabulary? If not, the architecture may be layered in folders only.

18. How do you move from “the API is slow” to a measured cause?

📈 A request trace is a timeline; metrics show whether the symptom is systemic
Symptom + SLO → correlated trace → slow span → dependency evidence → measured change

Start with a user-visible symptom and a time window: latency percentile, error rate, throughput, and affected route or release. Metrics reveal whether the issue is broad or localized. A distributed trace follows one request across middleware, application work, database calls, and downstream HTTP; spans expose where time was spent. Structured logs provide contextual events. Correlate with trace IDs, but do not use high-cardinality identifiers as metric labels.

If time is inside SQL, inspect generated SQL, query plan, indexes, connection wait, and row count. If time is before dependencies, inspect CPU, thread-pool queue, locks, allocation, and GC pauses. If one remote span dominates, inspect its timeout, connection pool, and service health. Make one change, rerun a representative load or benchmark, compare the same percentiles and resource costs, and retain the change only if the evidence improves.

Measure baseline → form hypothesis → change one cause → replay/load test → compare latency, errors, CPU, allocations, DB load
Operational rule: Instrument boundaries without recording secrets or sensitive payloads. Sampling, retention, alert thresholds, and cardinality are part of observability design—not afterthoughts.
