Patterns explained through the same checkout

1. API Gateway / Backend for Frontend

What it solves

One secure client entry point, with a tailored API for each user experience when needed.

In the shop

The app calls POST /checkout; the gateway validates the token, applies rate limits, and routes to Checkout. A mobile BFF can return a smaller response than a web BFF.

2. Database per service

What it solves

Service autonomy and ownership of business rules and persisted data.

In the shop

Inventory owns stock; Payment owns payment records. Other services use APIs or events, not direct SQL into another service's tables.

3. Event-driven / Publish-subscribe

What it solves

Decouples work that does not need to finish before the current request returns.

In the shop

After an order is accepted, subscribers update analytics, send a receipt, and start fulfillment from OrderPlaced.

4. Saga

What it solves

A multi-service business transaction without a distributed database transaction.

In the shop

Reserve stock → authorize payment → confirm order. If payment fails, release the reservation; if stock fails, do not capture payment. Each compensation is an explicit business action.

5. Transactional Outbox

What it solves

Prevents a database update succeeding while its event is lost (or an event being published for a rolled-back update).

In the shop

Order Service commits the order and an outbox row in one local transaction. A publisher retries delivery; consumers deduplicate because delivery is typically at least once.

6. CQRS

What it solves

Lets write rules and high-volume read models evolve independently where workload justifies it.

In the shop

Checkout writes an order to its authoritative store; a read projection serves the order-history screen. The projection may lag briefly, so the UI handles eventual consistency.

7. Event sourcing

What it solves

Stores an append-only sequence of domain events as the source of truth when audit and historical reconstruction justify the complexity.

In the shop

An order stream could record OrderCreated, InventoryReserved, and OrderConfirmed. It is not required just because the system publishes integration events.

8. Cache-aside

What it solves

Reduces repeated reads and latency for data that can tolerate a freshness window.

In the shop

Catalog reads check a cache first and load from the catalog store on a miss. Use short TTLs or invalidation for price changes; never trust a cached stock count as the final reservation.

9. Retry with backoff and jitter

What it solves

Recovers from transient timeouts without retry storms.

In the shop

Retry a timed-out inventory request with bounded exponential backoff and jitter only when the operation is safe to repeat (or has an idempotency key).

10. Circuit breaker

What it solves

Stops repeatedly calling a failing dependency and gives it time to recover.

In the shop

If the recommendation service is down, open the breaker and render the product page without recommendations instead of delaying checkout.

11. Bulkhead and timeout

What it solves

Limits resource exhaustion and prevents one slow dependency consuming all request capacity.

In the shop

Give recommendations a separate connection pool and short deadline. Checkout retains its own capacity when recommendations are slow.

12. Idempotency

What it solves

Makes a repeated request safe when a client retries after a timeout or loses the response.

In the shop

The client sends an idempotency key with checkout. The service stores the key and result so a retry returns the same order instead of charging twice.

13. State machine

What it solves

Defines valid state transitions and rejects impossible or duplicate actions.

In the shop

An order can move from PENDING_PAYMENT to CONFIRMED or CANCELLED; it cannot move from SHIPPED back to PAYMENT_PENDING.

14. Dead-letter queue

What it solves

Isolates messages that still fail after bounded retries for inspection and safe replay.

In the shop

A malformed shipment event is moved to a DLQ with diagnostics and an alert; operators fix the cause and replay it with duplicate protection.

15. Strategy, Factory, Builder, Repository

What they solve

Keep variation, object construction, and persistence details out of core business decisions.

In the shop

A shipping strategy chooses a carrier by destination and promise; a factory creates the right carrier adapter; a builder assembles a complex shipment request; a repository persists the order aggregate behind a domain-facing interface.

16. Service discovery and observability

What they solve

Finds healthy service instances and makes cross-service behavior diagnosable.

In the shop

Runtime routing targets healthy Inventory instances. A trace ID follows checkout across services; metrics track latency, errors, queue lag, and reservation failures.

17. Strangler Fig and anti-corruption layer

What they solve

Replace a legacy system incrementally while keeping its data model from leaking into new domain code.

In the shop

Route new checkout flows to Order Service while legacy order history remains available. An adapter translates the old order format into the new contract.

18. Sidecar / Ambassador

What they solve

Moves cross-cutting network or runtime concerns alongside an application or into a dedicated proxy.

In the shop

A sidecar can export telemetry or enforce service-mesh policy; an outbound proxy can centralize controlled calls to a payment provider. Use only when platform operations benefit.

19. API Composition

What it solves

Builds a client-facing view by querying multiple service-owned read models.

In the shop

An order-details endpoint combines order and shipment summaries. Set deadlines and partial-response behavior so one optional dependency does not stall the whole page.

Choose patterns for a reason: a monolith may be simpler for an early product. Add a separate service or an event-driven projection when independent ownership, scale, release cadence, or failure isolation pays for the operational cost.

Low-Level Design: Amazon-Scale Retail Store

An interview-ready, illustrative design for a large online marketplace: catalog, cart, checkout, inventory reservation, payment, order tracking, and fulfillment. This is a teaching example, not a description of Amazon's proprietary internal architecture.

Scope and assumptions: customers browse products, add offers to a cart, place an order, pay, and track delivery. A marketplace offer is seller + product + price + availability. The design prioritizes no duplicate charges, no overselling beyond configured policy, fast reads, and eventual consistency for non-critical views.

Service ownership and responsibilities

Catalog Service

Owns product titles, descriptions, attributes, and media references. Publishes product changes to search indexing.

Does not own: order-time price snapshots or available-to-sell stock.

Search Service

Serves text search, facets, and ranking from a denormalized index. Index updates are asynchronous.

Trade-off: search can lag catalog edits; product detail reads the authoritative catalog.

Cart Service

Stores customer cart lines, selected offer, quantity, and an optimistic version. Revalidates price and availability at checkout.

Storage: partition by customer/cart ID with a TTL for abandoned carts.

Checkout / Order Service

Validates the request, snapshots item/offer/price/address, creates the order, and coordinates saga steps.

Owns: order lifecycle, idempotency records, and its outbox.

Inventory Service

Owns stock by SKU and fulfillment location. Atomically reserves or rejects requested quantities with an expiry.

Invariant: active reservations plus committed allocations cannot exceed sellable stock.

Payment Service

Owns payment attempts and provider tokens. Authorizes through a provider adapter and captures only at the chosen fulfillment milestone.

Security: do not store raw card numbers; use a compliant payment provider/tokenization flow.

Fulfillment Service

Creates warehouse work after order confirmation, tracks package and carrier status, and emits shipment events.

Downstream: notification consumers send email, push, or SMS without blocking order writes.

Identity, Pricing, and Delivery Promise

Identity authenticates customers; Pricing calculates eligible offer, tax, and discounts; Promise estimates delivery dates.

Boundary: checkout stores the final quoted amounts and terms on the order for an auditable purchase.

Checkout sequence: reserve, authorize, confirm

  1. Client → Checkout: send cart, address, payment token, and idempotency key. Authenticate and validate request shape.
  2. Checkout → Cart / Pricing: verify cart version, re-price every offer, calculate tax and delivery, and freeze an order snapshot.
  3. Checkout → Order store: create PENDING order plus CheckoutStarted outbox record in one local transaction; return the same order for duplicate idempotency keys.
  4. Order saga → Inventory: atomically reserve all lines (or fail the reservation) with a bounded expiry. Emit InventoryReserved.
  5. Order saga → Payment: authorize the total using a stable provider idempotency reference. Do not expose payment secrets to other services.
  6. Order store: transition to CONFIRMED, persist OrderConfirmed in the outbox, and return the order ID/status to the client.
  7. Async consumers: fulfillment creates warehouse work; notification sends confirmation; analytics updates its projection. Each consumer deduplicates event IDs.
  8. Failure compensation: if authorization is declined, release inventory and mark the order PAYMENT_FAILED. If a later step fails, execute the explicit compensation and alert when compensation itself needs intervention.

Order state and failure handling

Transitions are validated by the Order Service; shipment and refund events are separate milestones.

PENDING→ RESERVING→ PAYMENT_AUTHORIZED→ CONFIRMED→ FULFILLING→ SHIPPED→ DELIVERED
PENDING→ CANCELLED PAYMENT_AUTHORIZED→ PAYMENT_FAILED CONFIRMED→ CANCEL_REQUESTED→ REFUND_PENDING
Payment timeout is ambiguous: the provider may have authorized the payment even if the response was lost. Query or retry using the same provider idempotency reference; do not create a fresh charge attempt until the first outcome is known.

Concurrency, scale, and reliability choices

Prevent overselling

Reserve with a conditional atomic update or serializable transaction on the inventory owner. Model per-location stock; expire abandoned reservations and release them idempotently.

Partition for traffic

Partition carts/orders by customer or order ID and inventory by SKU + location. Avoid a single global hot counter; use regional inventory pools or controlled allocation where the business allows.

Handle duplicate / out-of-order events

Give every event an ID and aggregate version. Consumers persist their inbox receipt and apply only valid transitions; make handlers safe to replay.

Protect service capacity

Set deadlines per dependency, bounded retries with jitter, circuit breakers, bulkheads, queue limits, and backpressure. Shed optional work before checkout work.

Separate critical and flexible consistency

Order and payment state require authoritative writes. Search, recommendations, and customer order-history projections can be eventually consistent with visible freshness/status.

Security and privacy

Authenticate every client request, authorize order ownership, encrypt data in transit/at rest, use least-privilege service identities, redact PII from logs, and use a PCI-compliant payment provider.

How to present this LLD in an interview

  1. Clarify scope, marketplace vs. first-party offers, traffic shape, stock policy, payment milestones, and delivery requirements.
  2. Define functional and non-functional requirements before choosing databases or queues.
  3. Draw service boundaries around ownership and invariants; state which calls are synchronous and which are events.
  4. Walk the checkout saga and explain idempotency, payment ambiguity, inventory reservation, and compensating actions.
  5. Show core entities, keys, indexes, concurrency controls, and one event contract.
  6. Close with bottlenecks, failure modes, observability, security, and the trade-offs of eventual consistency.

Why It Matters

This platform is designed for enterprise-scale, customer-facing operations where conversations must be routed quickly, reliably, and with the correct business context. It balances performance, resilience, security, and scalability while supporting multiple channels and complex work assignment logic.

In interview terms: “CRM.Omnichannel is a cloud-native, microservice-based, event-driven customer service platform built on Azure and .NET. It supports omnichannel engagement, intelligent routing, and real-time agent coordination, using patterns like CQRS, event-driven integration, retry/circuit-breaker resiliency, and state-driven workflow processing.”
