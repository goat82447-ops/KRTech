Design an Amazon-scale Marketplace

Requirements → service boundaries → technology choices → request flows → data model → failure handling. A complete, interview-style design for a large online retail application.

Important: this is an illustrative design for an Amazon-like marketplace. It is not a claim about Amazon's internal or proprietary architecture. Capacity numbers are explicit planning assumptions, not reported Amazon traffic.

1. Define scope and requirements

Start by defining the product and its constraints. For this case study, “Amazon application” means a global marketplace experience: customers discover products, buy seller offers, pay, and track delivery.

Functional requirements

  • Browse categories and product detail pages; search, filter, sort, and view product media.
  • Represent a marketplace offer as a seller's price, condition, and fulfillment option for a product.
  • Create and update a persistent cart across sessions and devices.
  • Validate price, promotions, address, tax, delivery promise, and stock at checkout.
  • Place an order, authorize payment, reserve inventory, and support safe retries.
  • Track order, shipment, delivery, cancellation, refund, and customer notification status.
  • Seller workflows to manage offers and inventory are in scope as a separate authenticated surface.

Out of scope for the first version

  • Detailed recommendation / ads ranking and machine-learning model training.
  • Warehouse robotics and route optimization internals.
  • Every region's tax, legal, and payment-provider integration.
  • Digital goods, subscriptions, auctions, and grocery cold-chain handling.

These can be additional domains behind stable APIs and events without entangling the core purchase flow.

Non-functional requirements (illustrative targets)

  • Availability: browse/search target 99.99%; order placement target 99.95%, measured monthly.
  • Latency: product/search p95 < 300 ms at edge/API; checkout orchestration response p95 < 2 s excluding external step-up authentication.
  • Durability: acknowledged order and payment state must survive a single node/AZ failure.
  • Correctness: no duplicate charge for one idempotency key; inventory reservation is atomic per stock owner.
  • Consistency: strong consistency for order transitions and stock reservation; bounded eventual consistency for search and read projections.
  • Security: least privilege, encryption, auditability, privacy controls, and payment-card compliance.
  • Operability: end-to-end traceability, reversible deployments, tested recovery, and controlled regional failover.

Why separate browse from buy?

Browsing is a high-volume read path where caches and slightly stale indexes are acceptable. Checkout is lower-volume but correctness-critical: price and inventory must be revalidated and recorded authoritatively. Independent paths let each scale and fail differently.

3. High-Level Design (HLD)

Separate the edge, synchronous customer journeys, domain-owned data, and asynchronous event consumers. The arrows show the conceptual path, not every network hop.

HLD · SYSTEM ARCHITECTURE Services, data stores, and event flows

Solid arrows = request or owned-data path. Dashed green arrows = asynchronous event / projection path. Each domain store is shown beneath its owning service; services do not share tables.

Command path vs. event path

Commands ask an owner to perform a decision now (reserve inventory, authorize payment). Use synchronous calls only when the result is required to continue, with strict timeouts.

Events state a fact that already happened (order confirmed). Consumers react independently; retries and duplicate delivery are expected.

Trust boundaries

Clients enter through an edge protected by WAF and identity. Internal services use workload identity, authorization, and encrypted transport. Payment-provider and seller integrations are treated as external/untrusted dependencies.

6. Main runtime flows

Browse and search

  1. Client requests a category/search page. CDN serves static assets and only caches public responses with an explicit cache key and policy.
  2. API/BFF authenticates when necessary, validates query limits, and calls Search. Search reads its own index, not a fan-out of service databases.
  3. Search returns product and offer IDs; BFF fetches/cache-reads presentation details in bounded batches, avoiding N+1 calls.
  4. Product detail checks Catalog and current Offer. Displayed availability is an estimate; final stock is checked at checkout.
  5. Catalog/Offer changes publish events through outbox; indexer updates OpenSearch idempotently. Track indexing lag as a metric.

Checkout (orchestrated saga)

  1. Client sends POST /v1/checkouts with cart ID/version, address ID, payment token reference, and a unique Idempotency-Key.
  2. Checkout returns an existing result for the same customer/key; otherwise validates identity, cart version, seller/offer eligibility, price, tax, address, and delivery promise.
  3. Order Service writes PENDING order, immutable item/price/address snapshots, saga state, and an outbox event in one local DB transaction.
  4. Saga requests Inventory to reserve all lines atomically with a stable order/attempt key and an expiry. Inventory returns reserved or rejected; partial reservation is rolled back inside the inventory owner.
  5. Payment authorizes the amount with a stable provider idempotency key. A timeout is an unknown outcome, not proof of failure; query/retry using the same key.
  6. On success, Order transitions to CONFIRMED and publishes OrderConfirmed from the outbox. Return order ID and status to client.
  7. Fulfillment consumes the event and creates work; Notification and Analytics consume independently. Consumers store event IDs to make at-least-once delivery safe.
  8. If authorization is declined, release the reservation and mark payment/order failed. If later cancellation occurs, void authorization or refund according to whether capture already happened.
PENDING→RESERVING→PAYMENT_AUTHORIZED→CONFIRMED→FULFILLING→SHIPPED / DELIVERED
Compensation is a business operation: release reservation, void authorization, cancel fulfillment, or issue refund. It is not a database rollback across services. If compensation fails, retain a visible pending state, retry safely, and alert operations/customer support.

LLD · DATA MODEL Order and inventory entity relationships

These are logical ownership relationships; each service owns its own database. The lines are domain references/events, not cross-service foreign keys.

Inventory reservation algorithm

The exact query varies by database. The invariant is that reservation and available-quantity check happen atomically at the Inventory owner; never perform “read quantity, then write quantity” as two unprotected calls.

reserve(orderId, sku, locationId, quantity, attemptKey):
  begin local transaction
    if reservation exists for attemptKey:
      return its recorded result

    updated = conditional update Stock
      set available = available - quantity,
          version = version + 1
      where sku = sku
        and locationId = locationId
        and available >= quantity

    if updated row count != 1:
      record reservation as REJECTED (idempotently)
      commit
      return OUT_OF_STOCK

    insert Reservation(
      attemptKey, orderId, sku, locationId,
      quantity, status = ACTIVE, expiresAt
    )
  commit
  return RESERVED

On release/expiry, mark the reservation terminal exactly once and increment available stock in the same local transaction. A scheduled sweeper is a recovery mechanism; it must be safe to run repeatedly.

Checkout orchestration pseudocode

handleCheckout(customerId, idempotencyKey, request):
  existing = orders.findByCustomerAndKey(customerId, idempotencyKey)
  if existing: return existing.currentResult

  quote = pricing.validateAndQuote(request.cartId, request.cartVersion)
  order = orders.createPendingWithOutbox(
    customerId, idempotencyKey, quote.snapshot
  )

  try:
    reservation = inventory.reserve(order.id, quote.lines)
    if reservation.failed:
      orders.transition(order.id, PENDING, REJECTED)
      return rejected(order.id)

    payment = payments.authorize(
      order.id, quote.total, request.paymentToken,
      idempotencyKey = order.paymentAttemptKey
    )
    if payment.outcomeUnknown:
      orders.transition(order.id, RESERVING, PAYMENT_PENDING)
      scheduleReconciliation(order.id)
      return acceptedForProcessing(order.id)
    if payment.declined:
      inventory.release(reservation.id)
      orders.transition(order.id, RESERVING, PAYMENT_FAILED)
      return paymentFailed(order.id)

    orders.confirmAndWriteOutbox(order.id, payment.reference)
    return confirmed(order.id)
  catch transientFailure:
    persistSagaProgress(order.id)
    retryWithBoundedBackoffOrReconcile(order.id)
    return acceptedForProcessing(order.id)

8. Scaling, consistency, and failure handling

Cache the right things

Cache public product fragments and static media at the edge; use Redis for hot, short-lived data. Use TTL, version keys, stampede protection, and invalidation events. Do not use cache to authorize payment or promise stock.

Partition and avoid hot keys

Partition carts/orders by stable IDs and stock by SKU + fulfillment location. Monitor skew. For high-demand limited stock, use controlled allocation/queues rather than one globally contended counter.

Protect dependencies

Set timeouts/deadlines, bounded exponential retry with jitter, circuit breakers, bulkheads, connection limits, and load shedding. Retry only idempotent or deduplicated operations.

At-least-once events

Use transactional outbox, consumer inbox/deduplication, bounded retries, DLQ, replay tooling, and poison-message alerts. “Exactly once” across independent databases and brokers is not assumed.

Consistency by domain

Strong/transactional at order state transition and inventory reservation owner. Search, recommendations, and order-history projections may lag; expose clear processing status and measure lag.

Backpressure

Limit queue depth and in-flight work; autoscale on queue age/lag as well as CPU. When demand exceeds capacity, protect existing checkout and return controlled retryable responses.

9. Security, privacy, and day-2 operations

Security controls

  • OAuth/OIDC customer identity; validate issuer, audience, expiry, and authorization on every order operation.
  • Workload identity and least-privilege service-to-service access; separate roles by environment and service.
  • TLS in transit; encryption at rest with managed keys and rotation; secrets delivered from a secret manager.
  • Payment tokenization/provider-hosted capture; do not store/log primary account number or CVV.
  • Input validation, output encoding, CSRF protection where applicable, abuse controls, WAF, and seller API quotas.
  • PII classification, retention/deletion policy, access audit, log redaction, and region-aware residency controls.

Observability and SLOs

  • Propagate trace/correlation ID from edge through checkout, inventory, payment, and fulfillment.
  • Track request rate, error ratio, latency percentiles, saturation, queue age, outbox lag, payment pending age, reservation expiry, and search indexing lag.
  • Use business signals: checkout success rate, duplicate suppression, oversell/under-reservation incidents, refund time, and shipment update delay.
  • Page on user-impacting symptoms and burn rate, not every transient exception. Link dashboards/runbooks to alerts.

Deployment and recovery

  • Build immutable artifacts; scan dependencies/images; generate SBOM; sign and promote through dev, test, and production.
  • Schema migrations use expand → deploy → backfill → contract; old and new versions coexist during rollout.
  • Canary by region/traffic cohort, monitor SLO and business metrics, then progress or roll back.
  • Back up databases and event schemas; regularly test restore, failover, and replay—not just backup creation.

Reliability targets to agree with the business

Set separate SLOs for browse, search, checkout, payment reconciliation, and shipment tracking. Define RTO (time to recover) and RPO (acceptable data loss) per domain; order/payment data generally demands tighter recovery than recommendation caches.

10. Key trade-offs and interview summary

Decisions and costs

  • Microservices: independent scaling/ownership, but more network failures, observability, and deployment complexity.
  • SQL for orders: clear transactions and constraints, but partitioning and write scaling require deliberate design.
  • Search index: fast, rich reads, but it is a projection and can be stale or rebuilt.
  • Redis: lower latency and origin load, but adds invalidation, capacity, and fallback complexity.
  • Kafka vs. queues: retained replayable streams suit event history; work queues suit task dispatch. Operate only what the use case needs.
  • Multi-region: improves disaster recovery and latency, but synchronous global writes increase latency and split-brain risk.

Two-minute design summary

“I separate the public browse path from the purchase path. The edge/CDN protects and serves cacheable traffic; Search reads a denormalized index, while Catalog and Offer remain authoritative. Cart is versioned and ephemeral. Checkout owns an immutable order snapshot and orchestrates a saga: reserve inventory, authorize payment, confirm the order, then publish through a transactional outbox. Inventory uses an atomic conditional reservation, and payment calls use stable idempotency keys. Fulfillment and notifications consume events independently with deduplication. I use strong consistency for order and stock invariants and eventual consistency for search/read projections, with explicit timeouts, DLQs, reconciliation, SLOs, and multi-AZ recovery.”
