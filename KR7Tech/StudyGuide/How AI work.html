🌍 Real-world Example: How GPT, Claude, and Copilot Give a Response

Think of GPT or Claude as the reasoning engine, and Copilot as the complete work assistant that surrounds a model with instructions, work context, search, tools, security, and a user experience.

Example request: “What failed in last night’s pipeline?”

The user asks one sentence, but the system performs several hidden steps.
User → Copilot/App → Instructions → Context/Search → GPT or Claude → Response
Step 1: Receive the prompt. The application collects the user’s question, conversation context, identity, and system instructions.
Step 2: Decide what is needed. If the question can be answered from supplied context, the model generates directly. If current evidence is required, the application searches or uses a tool.
Important: GPT and Claude are model families. Copilot is an assistant or product experience that can use models together with work data, search, tools, and safety controls.

How the model creates the text

A model does not write the full answer in one operation.
Prompt → Tokens → Attention → Next-token probabilities → Token-by-token answer
Example: After reading “The pipeline failed because…”, the model estimates which next token is most suitable, selects it, and repeats until the response is complete.
Result: The response can sound natural because the model learned language patterns, but fluency alone does not prove correctness. Grounding and validation provide evidence.

GPT vs Claude vs Copilot

People often compare items from different layers.
Model: GPT / Claude → Application: Copilot / Agent → Data and Tools
GPT: A model family from OpenAI used for understanding and generation.
Claude: A model family from Anthropic used for understanding and generation.
Copilot: A Microsoft assistant experience that combines a model with prompts, grounding, search, applications, and enterprise controls.
Simple memory: Model = engine. Copilot = complete car. Agent = a car that can also choose a route and perform approved work.

🧠 Inside an LLM: What Happens After You Press Send?

A prompt is not a database query that looks up a finished answer. It is converted into tokens, processed through a neural network, and used to predict one next token at a time. This walkthrough explains the common Transformer-based path; exact model internals and optimizations vary and are often proprietary.

1 · The application builds the actual prompt

The visible text box is often only one piece of model input.
System/developer instructions + conversation + retrieved evidence + user message + tool definitions → serialized model input

A chat application may add system or developer instructions, recent conversation turns, summaries of older turns, retrieved passages, output-format rules, and tool schemas. It serializes these messages into the model's expected format. Some APIs also include image, audio, or other non-text inputs. The model only receives what the application sends within the request; an application may keep other data outside the model.

The context window is a finite token budget shared by the input and, depending on the service, generated output. If history grows too large, the product may truncate it, summarize it, or reject the request. That is why a long conversation is not guaranteed to be perfectly remembered.

Debugging question: What exact messages, retrieved evidence, tool definitions, and token limits reached the model? Log a privacy-safe request shape and token counts—not secrets or sensitive prompt contents.

2 · Tokenization and embeddings

The network processes numerical representations, not words as humans see them.
Text → tokenizer pieces → token IDs → learned embedding vectors

A tokenizer splits text into model-specific pieces. A token can be a whole common word, part of a word, punctuation, or whitespace; token count is not the same as word count. Each token ID maps to a learned vector. Position information is also represented so the model can distinguish order and relative location in the sequence.

Different tokenizers can encode the same text into different numbers of tokens. Code, uncommon names, and some languages can use more tokens than expected. More input tokens generally mean more prefill work, more context memory, and higher usage cost for metered APIs.

Practical impact: Keep instructions clear and context relevant. Repeating large policy text in every agent round wastes input budget unless the serving system can safely reuse cached prefixes.

3 · What attention does inside a Transformer

Each position builds a context-aware representation using other allowed positions.
Hidden vectors → Query / Key / Value projections → attention weights → mixed context

In a typical self-attention layer, learned projections produce query, key, and value vectors. A position compares its query with keys at permitted positions to calculate relevance weights, then combines their values. Multiple attention heads learn different relationships. A causal mask prevents a next-token model from using future answer tokens that it has not generated yet.

Transformer blocks also use feed-forward (MLP) layers, residual paths, normalization, and learned weights. Repeating these blocks transforms token representations into richer contextual features. Attention is not a literal human thought process or a guarantee that the model understands facts; it is a mathematical operation inside a trained network.

Memory: Attention mixes context; MLP layers transform each position's features; residual and normalization operations help deep networks train and operate.

4 · From hidden state to the next-token choice

Generation repeatedly ranks possible next tokens, then applies a decoding policy.
Final hidden state → vocabulary logits → sampling/selection → token appended

The output head maps the current representation to a score (logit) for each token in the model's vocabulary. A decoding method converts those scores into a next-token choice. Greedy decoding takes the highest-scoring option; sampling can use temperature, top-p, or related controls to vary the choice. These controls affect output variability; they do not add knowledge or verify correctness.

The chosen token is appended to the context and the model predicts again. Generation ends when it emits a stop token, reaches a configured limit, or the service stops the request. The result is decoded back into text. A tool-call response is still model output: the application must validate the requested tool, arguments, permissions, and result before continuing.

Conceptual pseudocode · not a provider SDK
tokens = tokenize(messages)
state = transformer_prefill(tokens)

while not stopped:
    logits = output_head(state.last_position)
    next_token = decode(logits, policy)
    if is_stop(next_token):
        break
    tokens.append(next_token)
    state = transformer_decode_next(tokens, cached_state)
Important: A fluent sentence is not proof of truth. The next-token objective rewards plausible continuation, not a built-in fact-check. Use trusted retrieval, tool verification, structured constraints, and evaluation when correctness matters.

5 · Why the first token and the rest have different latency

Prompt processing is parallelizable; autoregressive output has a sequential dependency.
Prefill input context → first-token latency → decode token 1 → decode token 2 → …

During prefill, the model processes the supplied prompt to build representations and attention state. Hardware can parallelize much of this work across input positions, although a longer context still takes more compute and memory. The service then produces the first output token; user-perceived time-to-first-token (TTFT) also includes network, queueing, routing, and service overhead.

During decode, each new token depends on previous generated tokens, so output proceeds step by step. A KV cache stores reusable keys and values from earlier positions so the model need not recompute the full prefix each time. It saves repeated work, but the cache consumes memory and each token still requires model computation. Long input and long output therefore affect different portions of total latency.

Measure separately: time-to-first-token, output tokens per second, total latency, queue time, input/output token counts, and retry/tool time. “Fast” can mean quick first response, high generation throughput, or low end-to-end time; these are not interchangeable.

6 · Why one model feels fast and another reasons more deeply

Speed and reasoning are product/model trade-offs—not a single “smartness” switch.
Latency ≈ queue + prefill + decode + network + tools/retries

A model can feel faster because it is smaller, uses fewer or more efficient active computations, runs on faster or closer hardware, has an optimized serving stack, receives a shorter prompt, emits fewer tokens, or is less busy. Quantization, batching, speculative decoding, caching, routing, and streaming can also change the measured experience. Providers do not always publish enough details to identify which factor dominates.

A fast model may show less reasoning depth if it uses a smaller capacity, has been tuned for concise answers, receives less inference-time thinking budget, or simply answers before exploring enough alternatives. A reasoning-focused model may take longer because it runs additional internal computation, generates more tokens, uses more complex decoding, or calls tools. More reasoning is not automatically more correct; extra steps can still make mistakes.

Model-name caution: “Astra” is not enough to identify a specific model and deployment. Exact speed and reasoning behavior depend on its provider, version, settings, region, prompt, load, and benchmark. Compare the exact model IDs under the same task and conditions rather than inferring internals from a name.
Choose with evaluations: Test representative easy, multi-step, coding, grounded, and no-answer tasks. Compare correctness, latency percentiles, token use, tool success, and cost—not one demo answer.

7 · Why “reasoning level low” can happen

A model cannot reason over evidence, steps, or budget it never received.
Ambiguous task + missing context + small budget + weak evaluation → shallow/incorrect answer

Common causes include an underspecified question, missing constraints, irrelevant or incomplete context, a small output limit, a model optimized for quick responses, low reasoning effort settings, or a request that does not ask for a structured explanation. In a multi-step task, the model may also need retrieval, calculation, code execution, or another tool rather than more prompt wording.

Improve the task contract: state the goal, assumptions, constraints, evidence sources, expected format, and what to do when information is missing. For critical calculations, use deterministic code; for current facts, retrieve trusted sources; for consequential actions, validate and require approval. Increasing the token budget can allow a longer response but does not guarantee better reasoning.

Prompt structure · guide the work, do not demand hidden chain-of-thought
Goal: Compare these two API designs for our stated workload.
Context: [trusted requirements and measured traffic]
Constraints: p95 under 200 ms; preserve tenant isolation.
Task: Identify assumptions, compare failure modes, and recommend one option.
Evidence: Cite the supplied requirement IDs; say when evidence is missing.
Output: Decision, trade-offs, risks, and validation plan.
Do not invent measurements or claim a test was run.
Evaluation over vibes: Score answer correctness, evidence use, coverage of constraints, calibration, latency, and cost on a repeatable test set. Do not rely on the model exposing private reasoning traces as proof of correctness.

8 · Why models hallucinate and how applications reduce risk

The model predicts likely output; it does not automatically check reality.
Uncertain/missing evidence → plausible token sequence → confident but unsupported claim

Training teaches statistical patterns from data; it does not turn every generated response into a database lookup with a truth guarantee. The model may generalize incorrectly, misread a prompt, blend conflicting context, or produce a plausible completion when evidence is absent. Sampling can change which completion appears but cannot establish truth.

Applications can reduce risk by retrieving authoritative sources, attaching citations that are checked against retrieved passages, validating structured outputs, running deterministic tools for exact work, stating uncertainty, and evaluating adversarial and no-answer cases. Retrieval also can be wrong: inspect access filters, freshness, ranking, and source quality.

Safe design: Keep authorization and business rules in trusted code. Treat retrieved text and tool output as untrusted input. Require human approval for sensitive writes, and make failures visible instead of returning a success-shaped guess.

🔄 Three Response Flows

Flow A: Generative AI response

Used when the model can answer from the prompt and its learned language patterns.
“Explain dependency injection” → Model → Explanation
What happens: The prompt is tokenized, the model interprets the context, and it generates the answer token by token.
Good for: Drafting, rewriting, brainstorming, summarizing supplied text, and explaining general concepts.

Flow B: Grounded RAG response

Used when the answer must come from current or private knowledge.
Question → Rewrite → Search → Retrieve evidence → Model → Answer + citations
Example: “What is our rollback procedure?” The system searches authorized team documentation, retrieves the most relevant sections, provides them to the model, and asks it to answer only from that evidence.
Good for: Policies, runbooks, project documentation, product knowledge, and enterprise Q&A.

Flow C: Agentic response and action

Used when a goal needs multiple decisions or real system actions.
Goal → Plan → Search/Tool → Observe → Next action → Verify → Respond
Example: “Investigate the failed pipeline and rerun only if the failure is transient.” The agent gathers run data, reads logs, retrieves the runbook, identifies the failure type, asks for approval when required, triggers a rerun, and checks the result.
Good for: Support workflows, pipeline operations, testing, ticket handling, and multistep business processes.

🔌 MCP Server, Client, Host, Tools, and Skills

MCP does not replace the model, RAG, or APIs. It gives an AI application a standard method to discover and call approved capabilities.

MCP architecture

Without a common protocol, every AI application needs custom integration code for every system.
Host App → MCP Client ↔ MCP Server → API / Database / Files / Azure DevOps
Host: The user-facing application, such as an agent app or supported Copilot experience.
Client: The component inside the host that connects using MCP.
Server: The service that publishes available tools, resources, and prompts.
Backend: The real API, database, file store, or enterprise system.
Memory: MCP server is a controlled adapter. It describes each capability using a name, description, inputs, and outputs so the agent can select it.

Real example: Azure DevOps MCP server

The agent needs live pipeline information and approved actions.
Agent → list_pipeline_runs → get_logs → trigger_pipeline → Azure DevOps
Published tools might be: get pipeline runs, fetch logs, read work items, and trigger an approved pipeline. The model chooses a tool; the runtime validates identity and arguments; the MCP server calls Azure DevOps; the structured result goes back to the model.
Security boundary: The model proposes the call. The application and server enforce authentication, authorization, validation, approval, timeout, and audit.

Resource vs Tool vs Prompt vs Skill

These terms solve different needs.
Resource = Read | Tool = Act | Prompt = Template | Skill = Playbook
Resource: Data the agent can read, such as a runbook or API response.
Tool: An operation, such as fetch logs or trigger a pipeline.
Prompt: A reusable instruction template.
Skill: A repeatable procedure that tells the agent how to combine instructions and tools to complete a job.
Example skill: “Pipeline failure investigation” can define steps, required evidence, allowed tools, approval rules, stop conditions, and output format.

Why Generative AI was not enough

A chatbot could explain what to do but could not reliably access live systems, perform the work, or verify the outcome.
Prompt → Helpful text, but no real action
Limitations: stale knowledge, hallucination, no private data by default, no real-time state, no application permissions, and no multistep execution control.
Next step: RAG added trusted knowledge, tools added actions, memory added continuity, and orchestration added decision loops.

What makes a system agentic?

The system works toward a goal instead of generating only one response.
Goal + Model + Instructions + Knowledge + Tools + Memory + Loop + Guardrails
Agentic behavior: understand the goal, create or choose steps, call tools, inspect results, adapt the plan, ask for missing information or approval, verify success, and stop.
Not every task needs an agent. Use a direct model call for simple generation, RAG for knowledge answers, a deterministic workflow for predictable automation, and an agent when dynamic decisions are truly required.

🧱 How We Can Build It, Step by Step

Level 1: Build a useful GenAI assistant

UI → Model API → Prompt → Response
Choose one narrow use case, select a suitable model, define system instructions, send the prompt, validate the response, and capture feedback.
Example: Convert a production issue description into a structured ticket draft.

Level 2: Add enterprise knowledge with RAG

Documents → Chunk → Embed → Index → Retrieve → Generate
Connect authorized sources, preserve permissions and metadata, create an ingestion pipeline, implement keyword/vector/hybrid retrieval, add citations, and evaluate retrieval and groundedness.
Example: Answer support questions from runbooks and previous issue documentation.

Level 3: Add one safe tool

Model selects tool → Validate → Approve if needed → Execute → Return result
Start with a read-only tool, give it a narrow schema, use least privilege, validate arguments, set timeouts, log every call, and return structured errors.
Example: Retrieve the latest pipeline status before enabling any rerun action.

Level 4: Add an MCP server

Agent Host → MCP Client → MCP Server → Several approved systems
Define the capabilities, wrap existing APIs as focused tools/resources, implement identity and authorization, publish schemas, add telemetry, test with invalid and malicious inputs, and version the server.
Example: One engineering MCP server exposes pipeline, repository, work-item, and test-result capabilities.

Level 5: Add agent orchestration

Goal → Plan → Tool loop → Human gate → Verification → Finish
Define the goal and success criteria, available tools, maximum steps, cost and time budgets, approval points, retry and idempotency rules, stop conditions, memory policy, and escalation path.
Example: Diagnose a failed deployment, propose rollback, wait for approval, execute it, and verify service health.

Level 6: Productionize and improve

Offline eval → Security review → Shadow → Canary → Monitor → Rollback
Build scenario evaluations, inspect full traces, measure task success, grounding, tool accuracy, safety, latency, and cost, then release gradually with a kill switch.
Rule: Version the model, prompt, knowledge index, tools, MCP server, policies, and evaluations together.

A practical build sequence

0 · Choose one user job

Write one sentence: “An engineer asks why a pipeline failed; the assistant finds the relevant runbook, summarizes evidence, and can read the run status.” Define what success means, what it must never do, users, data sensitivity, and expected volume.

Why first: model choice and architecture depend on the task, not the other way around.

1 · Build a plain model call

Start with a backend endpoint, one system instruction, one user message, output limits, timeout, and structured response validation. Add an evaluation set of realistic questions before introducing retrieval or tools.

Why: establish a measurable baseline so new components can be proven useful.

2 · Add RAG for changing facts

Ingest approved documents, retain source and access metadata, chunk them, embed and index, retrieve relevant passages for each question, and give the model evidence with instructions to cite or abstain.

Why: changing company knowledge belongs in a controlled data source, not stale model weights.

3 · Add one read-only tool

Expose a narrow operation such as get_pipeline_status(run_id). Validate the schema and user access server-side, set a deadline, return a typed result, and log the call. Begin without write tools.

Why: live facts require a trusted system of record; free-form model knowledge is not enough.

4 · Add a bounded agent loop

Let the model request an allowlisted tool. The orchestrator validates arguments and policy, executes the tool, returns its result, and permits another step only within a strict step/time/token budget.

Why: multiple steps become useful when the next action depends on observed results.

5 · Add approvals for changes

For a rerun or deployment, show the exact target, environment, consequences, and evidence. Require explicit approval tied to the authenticated user and exact action; revalidate before execution.

Why: approval must authorize a specific action, not a vague conversational intention.

6 · Evaluate every layer

Measure answer correctness, retrieval recall, citation support, tool selection and arguments, policy violations, latency, cost, and task completion. Test missing data, irrelevant documents, malicious text, timeouts, duplicate calls, and denied permissions.

Why: an end-to-end answer can fail even when the model itself is healthy.

7 · Release and operate safely

Version prompts, model, tools, index, policy, and eval set. Use a staging environment, canary release, rate and budget limits, traces with sensitive-content redaction, kill switch, rollback, and an incident owner.

Why: changing any of these can change behavior, cost, or risk.

RAG: ingestion and question answering are two different pipelines

RAG (retrieval-augmented generation) retrieves evidence at request time and places it in the model's context. It does not retrain the model. Build ingestion separately from the interactive query path so documents can be reprocessed, audited, and indexed without blocking users.

Pipeline A · Ingest and index

Source → Parse/OCR → Normalize → Split → Metadata + ACL → Embed → Index → Reconcile/Delete
Why each step exists: parse extracts useful text; normalization removes format noise; chunking creates retrievable units; metadata preserves source/version/date/tenant/ACL; embeddings capture semantic similarity; the index enables search. Reconciliation removes deleted or newly unauthorized content.
Implementation choices: preserve stable document and chunk IDs; record source hash, parser/embedding version, timestamps, and access labels. Make ingestion idempotent and support re-indexing when chunk or embedding models change. Quarantine unsupported or malicious files; do not treat document instructions as trusted system instructions.

Pipeline B · Retrieve and answer

Question + Identity → Query rewrite → ACL filter → Keyword + Vector → Rerank → Evidence → Answer + citations / Abstain
Why each step exists: query rewriting resolves references; ACL filtering prevents unauthorized retrieval; keyword search catches exact IDs/error codes; vector search catches meaning; reranking improves ordering; citations connect claims to sources.
Must-have behavior: pass only authorized snippets; include source title, locator, and version; instruct the model to say when evidence is insufficient; validate citation IDs against retrieved results; provide a useful “not found” path instead of inventing facts.

Chunking: balance context and precision

Start with natural sections/paragraphs and a moderate target size appropriate to the embedding model and content—not one universal token number. Keep a small overlap only when a fact may cross boundaries. Retain headings and parent-document IDs so a short chunk is not detached from its meaning.

Too small: loses explanation and references. Too large: dilutes relevance and consumes context. Evaluate multiple chunk sizes using real questions, not intuition alone.

Retrieval quality: debug before prompt tweaking

For each test question, save the expected source passages. Measure whether retrieval finds them (recall@k), whether top results are relevant (precision/ranking), and whether the answer's claims are supported by citations. If the evidence is absent, a stronger generation prompt cannot fix retrieval.

Test exact identifiers, synonyms, multi-hop questions, no-answer questions, stale documents, duplicate content, tenant boundaries, and permission changes. Compare keyword, vector, hybrid, and reranked results.

Python · deterministic ingestion skeleton (keep extraction and embedding adapters replaceable)
def ingest_document(file, source, tenant_id, acl, parser, embedder, index):
    text = parser.extract(file)
    if not text.strip():
        raise ValueError("Document contains no searchable text")

    sections = split_by_headings_and_size(text)
    records = []
    for number, section in enumerate(sections):
        chunk_id = stable_id(source.id, source.version, number)
        records.append({
            "id": chunk_id,
            "text": section.text,
            "vector": embedder.embed(section.text),
            "metadata": {
                "source_id": source.id,
                "source_version": source.version,
                "heading": section.heading,
                "tenant_id": tenant_id,
                "allowed_principals": acl,
                "content_hash": hash_text(section.text),
            },
        })

    index.upsert(records)
    index.remove_missing_chunks(source.id, source.version, keep={r["id"] for r in records})
    return len(records)

The helpers above are intentionally adapters: use your parser, embedding model, and search index. Enforce ACL filters in the trusted retrieval service for every query; never rely on the prompt to enforce access. For sensitive data, avoid putting full retrieved text into general-purpose logs.

Give tools narrow contracts

Prefer get_pipeline_status(run_id) over run_any_command(command). Validate identifiers and tenant ownership server-side. Separate read and write tools. Give each tool a typed input/output schema, timeout, rate limit, error taxonomy, audit record, and least-privilege credential.

Make state and stopping explicit

Persist task ID, authenticated owner, current state, tool-call IDs, result references, attempt count, deadline, and approval state. Use a state machine such as Created → Running → AwaitingApproval → Succeeded/Failed/Cancelled. Stop on success, user cancellation, policy denial, step limit, deadline, or budget exhaustion.

Approval is a security check

For writes, show the exact action and parameters. Bind approval to a hash of the action, target, environment, and expiry; after approval, re-check current authorization and target state before execution. If any parameter changes, require fresh approval. Never let the model forge approval.

Prompt injection and untrusted evidence

Retrieved documents, web pages, tool output, and user input are data—not policy. An attacker may put instructions in any of them. Use explicit trust boundaries, tool allowlists, output validation, source ACLs, data minimization, and adversarial evaluations. The model is not the authorization boundary.

    message = result.choices[0].message
    messages.append(message.model_dump(exclude_none=True))

    if not message.tool_calls:
        print(message.content or "No answer was produced.")
        break

    for call in message.tool_calls:
        if call.function.name != "search_knowledge":
            raise RuntimeError("Tool is not allowlisted")
        args = json.loads(call.function.arguments)
        if set(args) != {"query"} or not isinstance(args["query"], str):
            raise ValueError("Invalid tool arguments")
        output = search_knowledge(args["query"])
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(output),
        })
else:
    raise RuntimeError("Agent step budget exhausted")

Morning run: what happens in order

  1. The scheduler starts a run for a specific authenticated user and local date; it does not use a model to choose whose account to access.
  2. The orchestrator asks the model to plan a concise briefing. It may request an allowlisted read tool such as email summaries or today's calendar.
  3. The server validates every tool name and argument, checks the user's provider permissions, applies timeouts and result limits, and returns only necessary data.
  4. The model sees tool observations as untrusted content, may request another permitted read, then produces a structured briefing and draft suggestions.
  5. The server validates schema, recipients, source message IDs, and draft length; persists results with source references and run ID. It does not send anything.
  6. The user reviews each draft. A separate approval request is bound to the exact draft version and recipient; only then may a mail adapter send it.

Why send is not an agent tool

A model can misunderstand “reply,” infer the wrong recipient, follow malicious instructions inside an email, or draft text that the user would not endorse. Keeping sending out of the model's tool list means a prompt cannot directly trigger email delivery.

The UI must show recipient, subject, complete message, source conversation, and account identity. Approval is an explicit user action over that exact version. If content or recipient changes after approval, invalidate approval and ask again.

For a higher-risk organization, require approval for every message. For any future auto-send rule, define narrow policy-based exceptions in trusted code, test them, log them, and allow revocation; never rely on the model's own assertion that permission exists.

The provider adapter must use its documented idempotency/reconciliation capabilities; not every email API guarantees idempotent sending. If the provider cannot safely deduplicate, an unknown send outcome needs a status lookup or human reconciliation instead of an automatic resend.

What makes this truly agentic?

The model chooses which authorized read to perform next based on the goal and observations. If calendar context changes priority, it can read tasks; if no email is relevant, it can stop early. A fixed sequence is still a valid workflow, but the model-driven tool/observation loop is agentic because next steps depend on results.

Where deterministic code remains better

Identity, data access, date ranges, quotas, deduplication, draft persistence, approval, send, and audit are deterministic policy. The model handles flexible interpretation, summarization, and draft wording. Do not ask a model to perform exact arithmetic, enforce authorization, or own irreversible state transitions.

Failure drills before real inbox access

Test prompt injection inside an email, wrong-recipient draft, empty calendar, expired OAuth token, provider rate limit, duplicate scheduled run, tool timeout, oversized mailbox, malformed model JSON, user cancellation, edited draft after approval, and send timeout with unknown delivery. Verify safe stop, useful error, audit trail, and no duplicate send.
